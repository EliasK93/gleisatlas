# Pattern analysis

## 1 Overview

Shows when and where rail traffic is unreliable: a weekday × hour heatmap of arrival punctuality, filterable by train category, station and month range. Cancellations are reported separately from delays. This is the v0.1 core (SPEC F2). The heatmap can also show one line, and the Rankings list, beside the stations and lines, the network-wide worst and best sections between two stops and records independent of delays: the most and fewest stops of a station, the most and fewest trains an hour of a line.

## 2 Spec

Metrics per heatmap cell (weekday 0 = Monday, hour 0–23):

- median and P90 arrival delay in minutes (non-cancelled stops only)
- share of arrivals under 6 minutes ("pünktlich", DB definition)
- cancellation rate (separate from the delay metrics)
- n, the number of stops including cancellations, and the covered period (`von`, `bis`)

Filters: train category (`alle`, `regional`, `fern`), station by EVA, month range (`YYYY-MM`, inclusive). `/karte` alone also takes days (`YYYY-MM-DD`) for `von` and `bis`, or a mix: a month `von` means its first day, a month `bis` its last day. Where `von` is omitted, the heatmap, the map and the station statistics start at `vollabdeckung_ab`, the first month with full station coverage (see §3; on the map its first day); `bis` defaults to the last month (on the map the last day in the data). A `bis` before `vollabdeckung_ab` switches that default off: the selection then starts at the first month (on the map the first day in the file).

Current API:

- `GET /heatmap` – query parameters: `gattung` (`alle` default, `regional`, `fern`), `eva` (station EVA, digits only, optional) or `linie` (a line key, at most 200 characters, optional; at most one of the two), `von` and `bis` (month `YYYY-MM`, optional, inclusive). Returns `von`, `bis`, `n`, `titel` (the line label for a `linie`, null otherwise), `cells` (`weekday`, `hour`, `n`, `ausfallquote`, `median`, `p90`, `puenktlich`) and `tage` (the same statistics per weekday over all hours, from the summed histogram). With `linie` the cells come from `linien_stunden.parquet` and pool both directions of the line; 404 for an unknown line, 422 with `eva` and `linie` together. An empty selection returns `n = 0`, no cells and no days. The response is cached per process.
- `GET /karte` – query parameters: `gattung`, `von`, `bis` as for the heatmap, except that each of `von` and `bis` is a month or a day. It reads the day table, so the returned `von` and `bis` are the first and last day with data in the selection (`YYYY-MM-DD`; empty strings for an empty selection). Returns `von`, `bis`, `n` (all stops in the selection), `ohne_koordinaten` (named stations with stops in the selection but no coordinates) and `stationen` (`eva`, `name`, `lat`, `lon` and the four statistics of the heatmap cell). Only stations with coordinates are listed. The response is gzip-compressed and cached per process.
- `GET /stationen` – query parameters: `q` (case-insensitive substring of the name, at most 100 characters), `limit` (1–100, default 20). Returns `eva`, `name`, `land` (the state's code as on `/tageskarte`, null where the label is no German state) and `n` (stops over the data set). Name-prefix matches come first, then the busiest station, then the name.
- `GET /suche` – the global search over stations and lines: query parameters `q` (1–100 characters) and `limit` (1–20, default 8, per group). Returns `bahnhoefe` (as `/stationen`), `linien` (`linie`, `label`, `typ`, `zug`, `richtung`, `ziel`) and `zuerst` (the group to list first). The rules are in [map.md](map.md) (Search). The line table behind it is cached per process and follows the file modification times.
- `GET /stationen/{eva}` – one station as `Station` (`eva`, `name`, `land` as above, `n`); 404 for an unknown EVA.
- `GET /stationen/{eva}/statistik` – query parameters: `gattung`, `von`, `bis`. Returns the `station`, `von`, `bis`, `n`, `gesamt` (the four statistics), `verteilung` (non-cancelled stops in 7 delay bins, edges in whole minutes: < 1, [1, 3), [3, 6), [6, 10), [10, 20), [20, 30), ≥ 30), `ausgefallen` (cancelled stops; `verteilung` plus `ausgefallen` sums to `n`) and `gruppen` (the statistics per `regional` and `fern`, only groups with stops). An empty selection returns `n = 0`, `gesamt` null and no bins; 404 for an unknown EVA.
- `GET /datenstand` – `monate` (months in `data/monate.parquet`), `bahnhoefe` (number of named stations), `vollabdeckung_ab` (`YYYY-MM`, the first month with at least half as many stations as the largest month; empty if there are no months), `fehlende_stunden` (month → hours missing in the source, only months with gaps) and `fahrplanwechsel` (ISO dates of the timetable changes inside the data range), `erster_tag` and `letzter_tag` (ISO dates of the first and last complete calendar day of the data), `fehlende_stunden_tage` (day → hours missing in the source, only days with gaps), `live_tage` (the ISO days after `letzter_tag` that the collector kept) and `heute`, `heute_stand`, `heute_stand_rest` (today's date when there is data for today so far, and the time of each source; see [day-history.md](day-history.md)). `monate`, `vollabdeckung_ab`, `fehlende_stunden` and `fahrplanwechsel` come from `data/monate.parquet` (override: `MONATE_PATH`), the three day fields from `data/tage.parquet` (override: `TAGE_PATH`).
- `GET /rankings` – query parameters: `typ` (required: `linien` or `bahnhoefe`), `metrik` (`puenktlich` default, `median`, `p90`, `ausfallquote`), `art` (`linien` default or `zuege`, read for `typ=linien` only and ignored for stations: lines against single trains, see [lines.md](lines.md) §3; a line without live data never ranks), `min_n` (integer from 15 to 1,000,000, default 500), `gattung`, `von`, `bis` (as for the heatmap), `limit` (integer from 1 to 2,000, default 10: the lists end at `anzahl` or at the limit). Returns `typ`, `metrik`, `min_n`, `von`, `bis`, `anzahl` (entries that reach `min_n`, counted in arrived stops for the delay metrics and in all stops for `ausfallquote`, and have a value for the metric), `schlechteste` (worst first, at most `limit`) and `beste` (best first, at most `limit`). An entry is `id` (the EVA of a station, the `linie` key of a line), `name` (station name or line label), `typ` (train type of a line, null for a station) and the four statistics. Higher is better for `puenktlich`, lower for the other three; ties go to the larger n, then the name. An empty selection returns `von` and `bis` as empty strings, `anzahl = 0` and two empty lists.
- `GET /rankings/abschnitte` – the network-wide sections: query parameters `min_n` (integer from 15 to 1,000,000, default 500, counted in trips), `gattung`, `von`, `bis`, `limit` (as for `/rankings`). Returns `min_n`, `von`, `bis`, `anzahl` (sections that reach `min_n`), `schlechteste` (most minutes lost first, at most `limit`) and `beste` (most minutes made up first, at most `limit`). A row is `von_eva`, `von_name`, `nach_eva`, `nach_name` (a station pair in one direction), `n` (trips over it, all lines), `minuten` (the mean change of the delay over the section, two decimals; negative: made up), `linien_anzahl` and `linien`, the three lines with the most trips through the section (ties by id), each `id`, `label`, `n` and `richtung`. `richtung` is the line page's direction (1 or 2) in which the section is a row of the line's route, null when it is not ([lines.md](lines.md) §2). Ties in `minuten` go to the larger n, then the names. Lines without live data are left out, single trains count, and `gattung` keeps the trips of the lines of that group. An empty selection returns empty strings for `von` and `bis`, `anzahl = 0` and two empty lists.
- `GET /rankings/rekorde` – records independent of delays: query parameters `art` (required, `halte` or `takt`), `min_n`, `gattung`, `von`, `bis`, `limit` (as for `/rankings`). Returns `art`, `min_n`, `von`, `bis`, `anzahl`, `meiste` (highest value first, at most `limit`) and `wenigste` (lowest first, at most `limit`); an entry is `id` (the EVA of a station, the `linie` key of a line), `name`, `wert` (two decimals) and `n`. `halte`: stations with their stops per calendar day, every stop counted (cancelled stops and the stops where a train starts included), divided by the days of the station's own months in the period; `n` is the station's stops. `takt`: lines with their trains per hour, the trips starting between 06:00 and 21:59 divided by 16 hours and by the days of the months the line has stops in, both directions added; single trains, lines without live data and lines with fewer than one such trip a day on average are left out; `n` is the line's arrived stops, the sample of the line Rankings. Ties go to the larger n, then the name, and the order follows the unrounded value.
- `GET /stationen/{eva}/linien` – query parameters: `gattung`, `von`, `bis`. Returns every line that stops at the station in the selection, as `linie`, `name` (label), `typ` and the four statistics, worst punctuality first, then the larger n, then the name. Lines with too little data (the UI's rule: fewer than 15 stops or fewer than 15 arrived stops) come after all others, and lines without a value come last within each part. No minimum n. 404 for an unknown EVA.
- `GET /linie` and `GET /linie/abschnitte` – the page of one line: query parameters `linie` (required, at most 200 characters), `von`, `bis` (months, as for the heatmap). `/linie` returns the line's header, its axis (`achse`, EVAs in order) and its stations with the four statistics; `/linie/abschnitte` returns the sections between consecutive stops with their trips and mean minutes. 404 for an unknown line. The rules and the response fields are in [lines.md](lines.md) §2.
- `GET /zeitverlauf` – query parameters: `eva` (digits only) or `linie` (a line key, at most 200 characters), at most one of them, and `gattung`. Without `eva` and `linie` the series is nationwide. There is no `von` or `bis`: the series always covers every month of `/datenstand`. Returns `titel` (station name or line label, null nationwide) and `monate`, one row per month in ascending order: `monat` (`YYYY-MM`), `n` and the four statistics. A month without stops in the selection has `n = 0` and all statistics null. 404 for an unknown `eva` or `linie`; 422 when both are given.
- `GET /tagesverlauf` – the same series per day, for the nationwide selection or one station: query parameters `eva` (digits only) and `gattung`; no `linie`, `von` or `bis`, and unknown keys, a `linie` included, are ignored, so `?linie=…` answers with the nationwide days. Returns `titel` and `tage`, one row per calendar day of `/datenstand` in ascending order: `tag` (`YYYY-MM-DD`), `n`, the four statistics, `fehlende_stunden` (hours missing in the source on that day) and `trend`. A day without stops has `n = 0` and null statistics. `trend` holds the four metrics as a centred 28-day median over the days without gaps and with enough data to show a value (the UI's rule: at least 15 stops, for the delay metrics at least 15 arrived stops) and is null where the window has fewer than 14 values. 404 for an unknown `eva`; 422 for a bad `eva` or `gattung`. The decisions are in [day-history.md](day-history.md) §3.
- `GET /tageskarte` – the map of one day of the 131 large stations against its normal: query parameter `tag` (required, `YYYY-MM-DD`). Returns `tag`, `referenztage` (the days the normal rests on, nearest first), `fehlende_stunden`, `deutschland`, `deutschland_fern` and `deutschland_regional` (the day's four statistics plus `normal` and `klasse`, null without stops), `laender` (one per state with stops: `land`, `bahnhoefe`, `alle`, `fern`, `regional`, valued like Germany), `n`, `ohne_koordinaten` and `stationen` (as in `/karte`, each plus `land`, `normal` and `klasse`), and on today the fields of the sources. `normal` is the median of the same weekday over the previous 12 weeks without gap days and nationwide holidays, null per metric with fewer than 8 valid days; `klasse` is the step 1 (much better) to 5 (much worse), 3 as usual, from the deviation of the day's value from the normal divided by the spread of the reference days (1.4826 times the median absolute deviation, at least a floor per metric): the bands of z are in [day-history.md](day-history.md) §2. It is null without a shown value or a normal, and for Germany and the states on a day with missing hours. 404 for a day outside the data; 422 for a malformed or impossible date. The response is gzip-compressed and cached per process. The rules are in [day-history.md](day-history.md) §2 and §4.
- Invalid input returns 422: `limit` outside 1–100 on `/stationen` or below 1 on the three rankings routes, `von` or `bis` not matching `YYYY-MM` (on `/karte`: `YYYY-MM` or `YYYY-MM-DD`, and a real calendar date, so `2026-02-31` and `0000-01` are rejected), `eva` not all ASCII digits, `gattung` outside the three values, `typ`, `art` or `metrik` outside their values, a missing `art` on `/rankings/rekorde`, `min_n` below 15 or above 1,000,000, `limit` above 2,000 on the three rankings routes, `eva` together with `linie`, `q` over 100 characters and `linie` over 200.
- Responses are gzip-compressed (`GZipMiddleware`, level 5; the reason is in [map.md](map.md) §3).

**Rankings tabs.** `/muster/rankings` has one four-way switch, Linien · Bahnhöfe · Abschnitte · Rekorde. Period and Gattung apply to every tab and the minimum-sample chips to all but Rekorde; the metric switch shows on Bahnhöfe and Linien only, and `k` stays in the URL on the other two, so switching back keeps the metric.

- **Abschnitte** shows two lists side by side (tabs on a narrow screen), "Verlieren am meisten Zeit" and "Holen am meisten auf". A row has the rank, "from → to", a small line with its trips and line count, and the mean minutes in the step colours and wording of the line page's sections ([lines.md](lines.md) §2). Under the pair stand the section's three busiest lines as links and "N weitere" when there are more. A line link opens the line page with the period and `k`, and with the direction and the section selected when the API gives a `richtung`; without one it opens the line page without a selection.
- **Rekorde** has a second switch, Halte · Züge, and two lists, "Die meisten" and "Die wenigsten". A row has the rank, the name (a station opens its page, a line its line page), the sample and the value: "1.618 Halte/Tag" (one decimal below 10, as in "3,2 Halte/Tag", a whole number from 10) or "29,4 Züge/h" (one decimal from 1 up, two below). On Züge the sample is replaced by "≈ 1,0 Züge am Tag" (the value times 16, formatted like the stops a day).
- A help line under the controls says what the tab counts. Abschnitte: the mean change of the delay per trip between two consecutive stops, per direction, all lines pooled (single trains included, lines without live data left out), the minimum counts trips. Halte: stops per calendar day of the months with data, every stop counted, a station needs at least 15 stops in the period. Züge: trains starting between 06:00 and 21:59 per day divided by 16, both directions added, train parts that run coupled counted separately, single trains and lines without live data left out, a line needs at least 15 stops in the period and on average at least one train a day between 6:00 and 21:59.

**Show more.** Every Rankings list starts with its first 10 rows and grows by 100 per click of "Mehr anzeigen" under it, until all rows are shown. Each list counts on its own, so the other list of the pair keeps its rows. Under the list a grey line counts the rows ("110 von 2.345", plain text); the button and the line disappear once the list is complete. A hidden polite region next to the count announces "{shown} Einträge angezeigt" only after a click in its own list, once the rows are there, never on load. The last click removes the button, so the focus moves to the first newly shown row (its link, or the row itself for a section row); before that the button keeps the focus. A list stops at 2,000 rows, the most the API serves: the button goes there and the count line stays ("2.000 von 2.445"). The count is not in the URL and falls back to 10 for both lists when the tab, a switch, the metric, the minimum, the Gattung or the period changes. The request names `limit` only above 10.

**Heatmap line filter.** `/muster/heatmap` takes the Zeitverlauf's "Linie" chip: a line sets `linie`, drops `bhf` and asks `/heatmap` for that line; the Linie chip shows its label. An unknown line shows the empty state of the Zeitverlauf with a way to clear `linie`.

The rest of the UI on top of this is described in [app-shell.md](app-shell.md) and [map.md](map.md).

## 3 Decisions

- **Percentiles come from the histogram**: smallest bucket whose cumulative count reaches q × N. Reason: aggregates store delay histograms in whole minutes, so cells can be merged under any filter.
- **Cancelled stops count in n and the cancellation rate, not in the delay distribution.** Reason: a cancellation is not a 0-minute delay (AC-7).
- **Stations are filtered by EVA, never by name.** Reason: names are not unique.
- **Every metric carries n and period.** Reason: AC-8, and uncertainty must be visible.
- **The default period starts at full coverage.** Without `von`, views start at `vollabdeckung_ab` (2025-11 on the real data), not at the first month. Reason: until 2025-10 the source covers only about 135 stations, so "nationwide" would silently mean the big hubs and every station panel would mix two different populations. The picker can still reach back to 2024-07.
- **Minimum n for rankings is user-set: 100, 500, 1,000 or 5,000 stops, default 500** (design.md §2.4). Reason: a line or station needs far more than 30 stops for a stable P90 over a period of months, and the right bar depends on the question. The cell rule of the heatmap (hatched below 15 stops) is separate. The UI offers the four values (not on the records, below); the API accepts any `min_n` from 15 to 1,000,000, the same floor as the heatmap's hatching.
- **Stations and lines are ranked by the same function** (`core/rankings.py`, `rank`). Reason: one ordering rule for both lists.
- **Only `/karte` takes days; the other routes keep months, and the month pages round days from a shared URL outward** (the rule is in [app-shell.md](app-shell.md) §2). Reason: the heatmap needs the hour and weekday, which only the month aggregate carries, and the lines have no day table; per-day tables for them would be much larger and not fit the deploy. Rounding outward keeps a link made on the Karte meaningful on the other pages, and the URL is left alone until a month select is changed, which writes months for both edges ([app-shell.md](app-shell.md) §2).
- **`min_n` counts arrived stops for the delay metrics (`puenktlich`, `median`, `p90`) and all stops for `ausfallquote`.** Reason: a median from a handful of arrived stops is as unstable as one from a handful of stops, and the UI shows "–" for it; a station with many stops but few arrivals would otherwise lead a ranking with a value the table hides. `anzahl` counts the entries that pass the same rule.
- **The line statistics are computed for every line, once per selection.** Reason: `rank()` already drops entries below `min_n`, so the line cache key has no `min_n` and dragging the threshold costs nothing after the first call (0.57 s cold for the default period).
- **`/zeitverlauf` always returns every month and marks empty months as holes.** A month without stops in the selection has `n = 0` and null statistics instead of being left out. Reason: the chart keeps one slot per month, so a gap shows as a gap and not as a shortened axis; the period picker does not apply to a series.
- **`Monat.ausfallquote` is nullable, unlike `Stats.ausfallquote`.** Reason: a month with `n = 0` has no cancellation rate, and 0 would claim that nothing was cancelled. For that reason `Monat` is its own model and does not inherit `Stats`; the JSON is `Stats` plus `monat`.
- **Line statistics on the station page and in the rankings have no minimum n in the API.** The station endpoint lists every line and the page shows the little-data rule per row; only `/rankings` applies a threshold. Reason: a station's line table is a lookup, a ranking is a claim.
- **Timetable changes are marked, not split.** The API names the mid-December dates and trains keep one key across years. Reason: product owner's choice (SPEC O6); a split per period comes with the planner. See [pipeline.md](pipeline.md) §3.
- **A line is its name, with the train type in front of a bare number, split into networks** (id `"{name}:{lowest EVA}"`). Reason: "S1" exists in many federal states. The label names the end stations. See [pipeline.md](pipeline.md) §3.
- **Weekday totals are computed in the API from the merged histogram**, not as a mean of cell values. Reason: percentiles and medians cannot be averaged.
- **Input is validated at the API.** Reason: a malformed `von` or a negative `limit` silently returned wrong data. `eva` accepts ASCII digits only, so a station name is never a key.
- **At most 4 Polars queries run at once per process** (`MAX_QUERIES` and `collect` in `backend/main.py`; every query goes through that one function). Reason: every route runs in FastAPI's thread pool (about 40 threads), and without a cap dozens of queries would compete for CPU and memory at once; requests beyond the cap wait. The cap does not prevent the Polars warning `POLARS_MAX_BLOCKING_THREAD_COUNT reached`, which also appears with one query at a time (see §8).
- **Sections are ranked per direction by the mean minutes per trip, with the line page's value and colour steps.** `abschnitte.parquet` is pooled over all lines by (from, to) without a new table; the two directions of a pair agree only loosely (r = 0.49 over the pairs), so each direction is its own row. Reason: the same number and colours as the line page make a row and the page it opens say the same thing. Single trains count and lines without live data are left out, since their minutes are not real. The minimum is in trips; the `min` chips keep their values (default 500).
- **The Gattung chip filters the sections by the group of the line.** A section counts the trips of the lines in that group, so "Fern" lists the ICE and IC sections on their own instead of the pooled section. Reason: the product owner's choice.
- **A section row names its three busiest lines as links, plus "N weitere".** Each carries the line page's `richtung` from the line's axis order, so `/linie/<id>?richtung=…&abschnitt=<from>-<to>` lands on the section. A line whose usual route does not contain the section (Hamburg → Berlin for the ICE 50x) has `richtung` null, and its link opens the line page without a selected section: 22 of the 57 named lines in the default view. Links from a section carry the period (`von`, `bis`) and `k`, so the line page shows the same minutes. Reason: the page can only select a section of its axis, and a link to nothing would be worse than a link to the line.
- **Trains per hour is the trips starting between 06:00 and 21:59 per day, divided by 16, both directions added.** Reason: "per operating hour" ties at 1.0 for every rare line, so the fewest list would be all ties, and a fixed daytime window makes lines comparable. A line id pools what the source names that line, so a line's number includes every train that runs under its name (RE1:08000001 holds RE 41xx and NX 268xx numbers).
- **A line is ranked only with at least one train a day between 06:00 and 21:59 on average (`MIN_TRIPS_PER_DAY`), and its row shows trains a day instead of the sample.** Without the rule the fewest list was full of 0,00: rare specials (vlx33, 43 stops, one daytime trip in three months) and night-only fragments of real lines (RB74:08000181, 2,746 stops, all trips around 03:00, 5 daytime trips in a year, against 16,000 to 31,000 for the real RB74 lines). The second line reads "≈ 1,0 Züge am Tag" (value × 16, one decimal below 10), which says more about a thin line than its stop count. Reason: the product owner's choice. Over 2025-11..2026-10 860 lines remain and the fewest list starts with RE56 Cottbus Hbf – Potsdam Hbf at 1.0 a day, then RB79 Neckarbischofsheim Nord – Mannheim Hbf and RE16 Trier Hbf – Apach.
- **Train parts that run coupled count separately, and the help line of Züge says so.** S1 Hamburg shows 29.4 trains an hour because the Airport and the Poppenbüttel part each count, 102 and 121 starts on a weekday, coupled from Ohlsdorf to Wedel; Berlin's S1 shows 18.2. Reason: the product owner's decision; a trip is counted once, by its first stop.
- **Station records are stops per calendar day over the period, from `halte.parquet`.** Every stop counts, cancelled ones and the stops where a train starts or ends included, because a terminus's starting trains are in no arrival count; the value is divided by the days of the station's own months in the period. Reason: a station that only has data in some months of the period is not diluted, and the minimum sample is the stop count, like `ausfallquote`.
- **Records and sections share the period and the Gattung of the other Rankings, and the metric switch is hidden on them.** Reason: they do not have a metric; keeping `k` in the URL lets a person return to Bahnhöfe or Linien with the metric they had.
- **The records have no minimum-sample chips: they ask the API for its lowest `min_n`, 15 (`LOW_N` in `metrics.ts`), and `min` stays in the URL for the other tabs, like `k`.** Reason: a threshold only made the "fewest" list show the stations right at the threshold. Over 2025-11..2026-10 the fewest-stops list with the floor reads Schönfließ Dorf (18 stops), Ehrang and Kainzenbad, then rarely served stations at about 1.3 stops a day; only 8 of 5,420 stations have less than one stop a day.
- **One four-way switch with a second switch for the records.** Linien · Bahnhöfe · Abschnitte · Rekorde on `typ` (the first two keep their order), and Halte · Züge on `rekord` as the first control of the controls card, shown on Rekorde only, like `art` on Linien. The header keeps only the type switch and Teilen, so the type switch stays where it is on every tab. Reason: the product owner's choice; the Rankings stay one page.
- **A line's heatmap pools both directions and uses the heatmap's selection chain.** The per-line table `linien_stunden.parquet` has the line where the aggregate has the station, and the Gattung goes through the same `selection()` as `/zeitverlauf`. Reason: a line has no station key to combine with, and a direction split would halve every cell; the sample is shown per cell as for stations. The API answers 422 for a station and a line together, as `/zeitverlauf` does.
- **The shown count is per list and not in the URL.** A shared link shows the top 10. Reason: the product owner's choice; a count in the URL would make a link carry the state of a click and need a key per list.
- **`limit` stays out of the cache keys: the cached functions keep the full ranking and the route slices it.** A click on "Mehr anzeigen" so asks the cache for what it already holds and recomputes nothing. The sections cache holds plain named tuples with interned strings and the route builds the response models for the slice only; the busiest lines are computed only for the sections that reach `min_n`. Reason: the models of all 14,193 sections took about 77 MB per cache entry, so 16 entries would take about 1.2 GB; the tuples take about 10.4 MB at `min_n` 500 and 7.9 MB at `min_n` 100, and interning the names saves 36 to 55 % of that.
- **The Rankings lists stop at 2,000 rows: `limit` is at most 2000 and `min_n` at most 1,000,000.** Reason: both were unbounded. `GET /rankings/abschnitte?limit=100000000` built about 33,000 models and a 12 MB body outside the query cap in up to 40 worker threads, which a few dozen parallel requests could turn into an out-of-memory restart of the 2 GiB container (each restart downloads every data file again); a 40-digit `min_n` reached Polars and answered 500 instead of 422; and every distinct `min_n` is a new cache entry. 2,000 rows are twenty clicks of "Mehr anzeigen", more than anyone reads, and the web app stops offering the button there.
- **The API's response models live in `backend/models.py`**, `backend/main.py` imports them. Reason: 37 models in 322 lines shared a 1,960-line file with the routes, the caches and the warm-up, so a model change and a route change collided and two writers could not work on the API at once. The move changed no byte of the OpenAPI schema (`backend/openapi.json` hashes the same before and after), and no test imports a model from `main`. The "no stops" values of `/linie`, `/zeitverlauf` and `/tagesverlauf` are one constant, `NO_VALUES`, so a fifth metric is one place less to forget.
- **`/zeitverlauf` is cached per selection** (`zeitverlauf_for`, §8). Reason: the nationwide monthly series scans and groups the whole aggregate and took about 0.9 s on every request (0.3 s for `gattung=fern`, 14 to 26 ms for a station or a line), and five at once fill the query cap; the warm-up leaves it out because the default view is the daily one.
- **Real figures, 2025-11 to 2026-10.** 14,193 sections reach 500 trips. The worst is Düsseldorf Hbf → Gelsenkirchen Hbf at +17.0 min (558 trips, 51 lines), the best Würzburg Hbf → Kassel-Wilhelmshöhe at −20.2 min. Berlin Ostkreuz has the most stops, 1,618 a day; S1 Wedel (Holst) – Hamburg-Poppenbüttel the most trains per hour, 29.4. The line-heatmap totals equal `lines.parquet` for every one of 81,588 line-months.

## 4 Architecture and data keys

- `backend/models.py` holds the Pydantic response models (`Stats`, `Station`, `Heatmap`, `Datenstand` and the rest, one place, imported by `backend/main.py`); `backend/main.py` holds the routes, the caches, the request log and the warm-up.
- `backend/main.py` loads `data/aggregate.parquet` (override: `AGGREGATE_PATH`), `data/stations.parquet` (override: `STATIONS_PATH`), `data/monate.parquet` (override: `MONATE_PATH`), `data/lines.parquet` (override: `LINES_PATH`) `data/linien.parquet` (override: `LINIEN_PATH`), `data/days.parquet` (override: `DAYS_PATH`), `data/tage.parquet` (override: `TAGE_PATH`), `data/abschnitte.parquet` (override: `ABSCHNITTE_PATH`) and `data/linienweg.parquet` (override: `LINIENWEG_PATH`) with Polars on each request. `monate.parquet` is required: without it every request without `von`, and `/datenstand`, fails. `tage.parquet` is also required by `/datenstand` and by `/tagesverlauf`, `days.parquet` by `/tagesverlauf`. `lines.parquet` and `linien.parquet` are required by `/rankings?typ=linien`, `/stationen/{eva}/linien` and `/zeitverlauf?linie=`. The two line-page files are required by `/linie` and `/linie/abschnitte` ([lines.md](lines.md) §4). `data/linien_stunden.parquet` (override: `LINIEN_STUNDEN_PATH`) is required by `/heatmap?linie=`, `data/halte.parquet` (`HALTE_PATH`) by `/rankings/rekorde?art=halte` and `data/takt.parquet` (`TAKT_PATH`) by `art=takt`; `/rankings/abschnitte` reads `abschnitte.parquet`, `linien.parquet`, `lines.parquet`, `linienweg.parquet` and `stations.parquet`. `pipeline.update` writes all of them; `/karte` and the rankings keep their results per process (see Known shortcuts). `/karte` reads `days.parquet`, not the aggregate.
- Aggregate keys: `weekday`, `hour`, `gruppe`, `eva`, `month`, `bucket`, `n` (see [pipeline.md](pipeline.md)). Line keys: `lines.parquet` has `linie`, `eva`, `gruppe`, `month`, `bucket`, `n` (no weekday or hour), `linien.parquet` has `linie`, `name`, `label`, `typ`, `zug`, `ohne_echtzeit`. The line statistics are therefore per month and category, not per cell, and the selection chain (`gattung`, `eva`, `von`, `bis`) is the one of the heatmap.
- `station_stats_for` (statistics per EVA for a month selection of the aggregate) feeds `/rankings?typ=bahnhoefe`; `karte_for` computes the same statistics per EVA from the day table (`stats_per_eva`) for `/karte`; `line_stats_for` feeds `/rankings?typ=linien`; `line_entries` also feeds `/stationen/{eva}/linien`. `/zeitverlauf` groups once by month and bucket and runs the statistics per month; `zeitverlauf_for` caches the month list per selection and the modification times of the source file (aggregate or lines) and of `monate.parquet`, while the route keeps the unknown-station and unknown-line checks outside the cache. `/tagesverlauf` does the same per day over `days.parquet` (keys `day`, `gruppe`, `eva`, `bucket`, `n`, see [pipeline.md](pipeline.md)), takes the gap hours from `tage.parquet`, and computes the trend in `trends`; `tage_for` caches the result per selection and the modification times of both files.
- `sections_for` (the pooled sections and their lines' directions) and `records_for` (`stops_per_day` and `trips_per_hour` feed it) are cached per process, at most 16 entries each, keyed by the files' modification times (`files_of`) and the selection; `heatmap_for` takes the line in its key. Both keep the whole ranking and the routes slice it by `limit`. The three routes are cheap: measured on the real data, the default selection answers the stop and train records in 0.2 s cold, and `sections_for` takes about 0.3 s cold (default period, `min_n` 500, 14,193 sections; the function timed in-process, the route itself not re-measured since the cache keeps every section). A sections entry holds about 10.4 MB at `min_n` 500 and 7.9 MB at `min_n` 100.
- The URL keys of the rankings and the heatmap (`typ`, `rekord`, `art`, `min`, `linie`) are in [app-shell.md](app-shell.md) §2.
- OpenAPI schema is exported to `backend/openapi.json` (`uv run python scripts/export_openapi.py`); the TypeScript client is generated from it, and the gate fails when either is stale.
- CORS allows the origins in `CORS_ORIGINS` (default `http://localhost:5317`), GET only; the deployed value is set in [deployment.md](deployment.md) §4.

## 8 Known shortcuts

- The query cap is one semaphore per process. Revisit with async routes or several replicas. Concurrent requests for the same uncached selection each run their own query; there is no single-flight.
- Polars' streaming engine (2.0.0, also 2.1.0) sometimes prints `POLARS_MAX_BLOCKING_THREAD_COUNT reached (512), this may indicate a deadlock` on the first group-by of a whole table in a fresh process (measured on the cold `/karte` when that read the aggregate). It is a false alarm: no query hangs, and the results equal the in-memory engine's. Measured in fresh processes: 2 of 20 runs of the plain query, about half of the cold bursts of the start-page requests, and also with one query at a time. The in-memory engine avoids it but makes a cold burst 2–3 times slower. Revisit with a newer Polars, or when the API log shows a request that does not finish.
- Some routes still re-read their parquet files on every request: `/stationen` and the name list behind it, and `/stationen/{eva}/statistik`. The heatmap, `/karte`, both rankings, `/zeitverlauf`, `/tagesverlauf` and `/tageskarte` keep results per process (below), and the small tables (`monate`, `tage`, `large`, today's and the live files) go through one cache keyed by path and modification time. Reconsider when the aggregate has grown much further.
- The lines at a station are not cached (`ponytail:` comment in `station_linien`): the biggest station takes about 0.1 s. Add an `lru_cache` like the rankings have if the page calls it often.
- The time series follows one selection (nationwide, one station or one line). Comparing up to three series in one chart is not built.
- A line id is `{name}:{lowest EVA of its network}` (`ponytail:` comment in `line_ids`). When a network gains a station with a lower EVA in a later month, its id changes, and a saved link to the old id returns 404. Accepted while the data only grows by whole months and a link is cheap to recreate from the rankings.
- The `/stationen` list omits the 6 EVAs that have no name in the source.
- **Train parts that run coupled count as separate trips** in the trains-per-hour records, so a line such as the Hamburg S1 reads 29.4 an hour. The Züge help line says so. Counting a coupled train once would need its parts paired first.
- **A section row may name a line whose usual route lacks the section.** Its link opens the line page without a selected section. Revisit if the rows end that way too often (§3 gives the share in the default view).
- **The line heatmap pools both directions** and reads `linien_stunden.parquet` (28.9 MB, 25 million rows) per request through the same selection as the other routes; `heatmap_for` keeps 16 results per process (`ponytail:` comment there). A heatmap per direction needs a `richtung` in the table.
- **The sections cache keeps about 10 MB per entry, 16 entries** (`ponytail:` comment on `sections_for`), up to about 160 MB with every entry filled. Lower `maxsize` if memory on the 2 GiB container gets tight.
- **The `/zeitverlauf` cache keeps 16 entries, one model per month** (`ponytail:` comment on `zeitverlauf_for`, per process like `tage_for`). Revisit when many different stations or lines are asked for. The nationwide month series is not in the warm-up, so the first `z=monat` view after a wake-up computes it (about 0.9 s locally on one thread); one line in `warm_up` would add it.
- **A failed "Mehr anzeigen" request replaces both lists with the error banner**, as a failed filter change does, and the raised counts stay, so "Erneut versuchen" asks again for the larger lists. Keeping the last good rows with an inline error is the upgrade if this bothers users.
- **The record tables and `linien_stunden` hold whole months only**, like the section tables: the current month's raw days are in none of them ([pipeline.md](pipeline.md) §8).
- `/karte`, the heatmap (`heatmap_for`, keyed by selection and the aggregate's modification time; about 1.9 s cold for the default period on one thread, so a warm-up after a wake-up pays off, [deployment.md](deployment.md) §3), the station statistics behind the station rankings, and the line statistics of the line rankings are each cached per process by selection and file modification time, at most 16 entries. The first `/karte` computation takes 2.7 s for the default range with one thread (5k Pydantic models; the earlier 3.6–4.0 s in [deployment.md](deployment.md) §3 was for the month aggregate). The statistics are already computed in Polars (`cells_of` over `cell_stats_frame`); measured on a year of days, that step gave no gain, since the scan and the group-by dominate, so a slower `/karte` needs a smaller scan. `/tagesverlauf` has the same kind of cache (`tage_for`, 16 entries, per process); its cost is in [day-history.md](day-history.md) §8.
