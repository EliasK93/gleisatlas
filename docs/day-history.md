# Day history

## 1 Overview

Day-level history: a daily time series with a 28-day trend in place of the monthly one (months stay as a switch), and the page Live-Lage (`/lage`), a map of the 131 large stations coloured by one day against its normal for that weekday, today by default. The page reads Germany, then the 16 Bundesländer, then the stations. Both rest on a per-day delay histogram. The Karte (`/karte`) shows a period of days for all stations, read from the same day table, but never one day against its normal ([map.md](map.md)). The planned feature direction is in SPEC §3.4; a calendar view and marked events come later.

**Coverage.** The day views reach the last complete day, usually yesterday: the days after the last monthly file are built from the source's raw responses and refreshed by `pipeline.update` (mechanics and the completeness rule: [pipeline.md](pipeline.md) §2, "Raw days"). Live-Lage reaches further where the collector has kept finished days after that ("Collector days" below). The month views (heatmap, rankings, monthly series, station sparkline) stay on whole months. When a month's file arrives, it replaces that month's raw days.

**Today.** Live-Lage opens on today so far, against the same hours of the reference days. The 131 large stations come from an own collector against the DB Timetables API, every 15 minutes; those the collector lacks fall back to the source's raw data of today, which runs up to about 10 hours behind. The source and hosting decision is [adr/0002-live-source.md](adr/0002-live-source.md); the collector and the partial day are in [pipeline.md](pipeline.md) §2. Today and the collector's days need the files `heute.parquet`, `live_tage.parquet` and `day_hours.parquet`: the API reads them from `data/`, and with `DATA_URL` it downloads them and keeps them current (below). The deployed site has them only if something puts them into the blob container.

## 2 Spec

**Daily time series** (`/muster/zeitverlauf`, nationwide or one station):

- One point per calendar day of the data: punctuality, cancellation rate, median and P90, each with `n`. A faint line shows the daily values, a bold line the trend.
- Days with missing source hours are drawn dashed and listed in the tooltip. They still show their own values but never feed the trend. The same goes for days with little data: a day feeds a metric's trend only when its value would be shown, by the same rule as the dashed days.
- Timetable changes stay marked. Days are the default view; a Tag/Monat switch returns to the monthly series. Line series and the station sparkline stay monthly.
- The table mode lists the days.

**Live-Lage** (`/lage`, optionally `?tag=YYYY-MM-DD`):

- **The page.** Live-Lage is the map of the large stations for one day: today where there is one, else the newest day with data (a collector day, else the last complete day), with a Rückblick to any earlier day. It shares the map code of the Karte (full-bleed map, legend, station panel) and lists only the 131 large stations, whatever the category: there is no Gattung switch and no period chip. The page ignores the keys `g`, `von` and `bis` but leaves them in the URL, so Karte → Live-Lage → Karte restores the Gattung and the period (§3). The Karte has no day mode.
- **Day and Rückblick.** Without `tag` the page shows the newest day (today, else the newest collector day, else the last complete day), so a bookmark always opens live. A past day is written as `tag`. The filter bar holds the metric switch, a native date field limited to the first day of `/datenstand` (2024-07) and the newest day, and three chips labelled "Letzte Tage": Heute, Gestern and Vorgestern, counted from the current day in Germany. A chip whose day has no map stays but is disabled and says why in its title and, for screen readers, in a hidden description (a touch screen shows no reason): "noch keine Daten für heute" for Heute before there is a today, "noch nicht vollständig" for a day that is neither complete nor kept by the collector, or before the first day of the data. Any other day is reached through the date field. On a phone the strip sits in one row with the other filters, which scrolls sideways (§3 and [app-shell.md](app-shell.md) §3). The pressed chip is the shown day, none for a day older than Vorgestern; the chip of the newest day removes `tag`. A day in the URL outside the data moves to the nearest edge, an impossible date is dropped, so the API is never asked for a day it has no data for. The date field writes a day to the URL only when it is complete and inside the data, so typing a year key by key neither moves the map nor queries the API. The keys are described in [app-shell.md](app-shell.md) §2.
- **Colour.** Each station is coloured by the step of its API `klasse` for the selected metric, on a five-step diverging scale from "viel besser" through "wie üblich" to "viel schlechter". The metric switch picks the metric. The API computes the step from z, the deviation of the day's value from the station's normal divided by the spread of the station's own reference days (§4). The sign is chosen so that better is positive. |z| below 1 is "wie üblich", 1 up to 2 is "besser" or "schlechter", 2 and more is "viel besser" or "viel schlechter". The frontend only maps the step to a colour.
- **Grey "kein Vergleich möglich".** A station is grey where there is nothing to compare: its value is not shown (the little-data rules of the period map apply to the day's `n`), it has only cancellations, or it has no normal. Grey dots draw below the coloured ones. The pale and very pale rules of the period map apply to the day's `n` too.
- **Legend.** The five step names under a diverging bar, the sentence "„Wie üblich“ heißt: innerhalb der gewohnten Schwankung der Station an diesem Wochentag" (no numbers: the limits differ per station), a grey key, the little-data and size keys, the line "Vergleichstage: n × weekday aus den 12 Wochen davor" and the meta line. The good/bad row of the period map is hidden. The labels and the panel name the day the data belongs to: while a new day loads, they keep the previous day's name.
- **Germany card.** A card above the legend is titled "Deutschland" on every day, today included, and names the day and its weekday, the value of the selected metric over all trains of the large stations and its normal ("üblich x"). A step block on its left shows the deviation, the value minus the normal in the metric's unit ("+4 min", "−4 %-Pkt.", "±0 min"), both rounded as shown before the subtraction, so "1 min · üblich 2 min" reads "−1 min", on the colour of Germany's `klasse` for the selected metric: the same five steps, colours and noise-aware rule as a station's dot (§3). Where there is no class (too few reference days, a value the UI does not show, a day with missing hours) the block is grey and reads "–". The block is named by the deviation and the step word ("−4 %-Pkt. · viel schlechter"), or "kein Vergleich möglich". Two secondary lines give the same metric for Fern and for Regional, each with a small step block, the value and "üblich x", or the no-comparison text where there is no normal. The step is never the only carrier: the block has its text label and the card shows the values.
- **Bundesländer.** The map opens at the overview: a card for each of the 16 states, in the colour of its step and with its deviation from the usual, over very faint station dots, a pale wash outside Germany and the state outlines.
  - **Value.** A state's value is pooled like Germany's: all stops of its large stations, with the same reference days, normal, class and gap rule (§3). On a gap day a state has no class either. On today a state counts the stations that report today, the set the Germany card uses, so the states add up to Germany. A station whose state is unknown keeps its dot and feeds Germany only. The API leaves out a state with no stops that day.
  - **Count.** Each state names how many large stations feed its value that day, by station name, not by EVA: Berlin reads "11 große Bahnhöfe" although it has 23 EVAs, and a state with one reads "1 großer Bahnhof".
  - **State cards.** One card per state, a button at a fixed anchor point on the map, in the step colour of the state's `klasse` for the selected metric with the deviation as its text ("+4 min", "−5 %-Pkt."), the same block as on the Germany card. Where the state has no class the card is grey and reads "–". Its name is the state, the deviation and the step word, or the reason; hovering shows the deviation, the value, "üblich x" and the station count. All 16 cards are always there: a state the API leaves out has a dashed card reading "–", named by its reason, "noch keine Daten für heute" on today and "Keine Daten für diesen Tag" on a past day. A live refresh updates the cards in place, so a focused one keeps the focus.
  - **Areas.** From `frontend/public/laender.geojson` (§4) the overview draws a pale wash outside Germany, a thin line between the states under a stronger outline of Germany, and a transparent area per state that takes a light tint on hover. Hovering a state's card or focusing it tints its area too. A hover over an area shows the same tooltip as its card.
  - **Overview and detail.** Up to one zoom step past the start view (the fit of Germany) the cards and the areas show and the dots are very faint (20 %, with no hover and no click: the state is the target). The wash and the lines fade out between that zoom and zoom 8, where the base map's own borders take over. Past the detail zoom the cards are hidden, the dots are full and hover and click work on them, as before. While a state is picked the detail zoom is the lower of that and the state's own fit zoom, so at the state's fit the dots are full; the state lines show as far as the fade allows (for Berlin, Hamburg and Bremen, which fit at zoom 8, they are gone and the base map's borders show); "← Deutschland" restores the normal one.
  - **Phone.** Below 768 px the start view and a state's fit keep clear of the bottom cards (the card and the legend): their measured top edge plus 12 px is the bottom padding, measured again whenever the cards change size, so no state card sits under the page card. The state cards are 28 px high there and show the number only, the unit stays in the name and the tooltip (44 px and the unit from 768 px on). The page card ends 56 px before the right edge, clear of the zoom buttons.
  - **Click.** A click on a state's card or area writes the key `land` (a lower-case state code such as `nw`), fits the map to the bounding box of that state's whole shape (all its polygons, so Bremen includes Bremerhaven; the zoom is capped at 8, so Berlin, Hamburg and Bremen keep their surroundings; on desktop the fit keeps clear of an open station panel) and turns the page card into the state's card: the state name, the count, the state's deviation, value and normal, Fern and Regional, and a "← Deutschland" button that removes `land` and fits Germany again. A state the day does not list gets its card too, with "0 große Bahnhöfe" and the reason in place of the values, and the fit works the same, since it needs the shape only. A code that is not a state shows Germany and is removed from the URL once. A click on the state already picked fits it again. After a pick the focus moves to the "← Deutschland" button, since the picked card goes with the zoom; after "← Deutschland" it moves to the map. `land` stays in the URL when the day changes and is dropped on every other page ([app-shell.md](app-shell.md) §2).
  - **API.** `/tageskarte` carries `laender`, a list of `Land` (`land`, `bahnhoefe`, `alle`, `fern`, `regional`, each value a `Deutschland` like the nationwide ones, with its `klasse`), and `TageskartenStation.land` (the state's code or null). `deutschland*` keep their names.
- **Gap note and empty day.** A day with missing source hours is selectable; the card adds "Datenlücke: n h fehlen" and its blocks are grey ("kein Vergleich möglich"), as are the state cards, never a step. The stations keep their steps. A day with no stops at the large stations (a gap day without data) shows the card with "Keine Daten für diesen Tag" and no stations.
- **Tooltip and panel.** The tooltip names the value, the normal and the step word ("never colour only"), or "kein Vergleich möglich". In the station panel each tile has a stripe in the step colour and the line "üblich x · step" or "kein Vergleich möglich"; the footer reads "n = … · weekday, date".

**Today on Live-Lage** (no `tag`, or `tag` = today):

- **When there is a today.** `/datenstand.heute` names the local date (Europe/Berlin) when at least one of the two sources holds data for it, that date is after `letzter_tag`, and `day_hours.parquet` exists. The live source counts only while its `stand` is under 2 hours old; the rest source has no age limit. Otherwise `heute` is null and the page ends at the last complete day.
- **Picker.** The date field and the Heute chip reach `heute`; Heute removes `tag`. A day in the URL after `letzter_tag` that is neither today nor a collector day moves to the newest day (today, else the newest collector day, else `letzter_tag`), including a day in between that is not complete yet.
- **Two sources.** The 131 large stations come from the collector (`data/heute.parquet`). A large station the collector's file lacks falls back to the partial raw day (`data/heute_rest.parquet`); no other station is listed. A station in the collector's file takes its values from there, the others from the rest file.
- **Cut at the last full hour.** Each source has a `stand`, the time its data was taken, and counts the arrivals planned before the full local hour of that `stand`: at 14:37 the stops planned 00:00 to 13:59. Each station's reference days are cut at the same hour as its source, so today and the normal cover the same hours.
- **Germany card.** On today it counts the large stations that report today, against the same stations and hours on the reference days; the text reads "Heute, Stand 14:37 · bis 14:00". The rule for which stations report today is the same for the main line and for the Fern and Regional lines. Where no station reports yet, the card falls back to the rest source's stations with the rest source's stand.
- **Legend.** The meta line names "Heute" instead of a date. One freshness line per source that holds data, each with its stand and cut, for example "Stand 14:37 · bis 14:00": "Große Bahnhöfe live: …" for the collector, "Übrige große Bahnhöfe: …" for the rest source where the collector holds data too, and "Große Bahnhöfe: …" where the rest source is the only one. A key for the grey stations reads "noch keine Daten für heute"; past days have no such key.
- **Tooltip and panel on today.** The tooltip adds the stand of the station's own source; the panel footer reads "n = … · Heute, Stand … · bis …" with that source's stand.
- **Grey stations.** On today every large station with coordinates that no source covers yet is listed with `n` = 0. A station without data today (`n` = 0) is drawn as the very pale grey ring, its tooltip reads "noch keine Daten für heute" and its panel says so in one sentence instead of the tiles.
- **Refresh.** While today is shown, the page asks `/tageskarte` again every 5 minutes; while `/datenstand` names a today, it is asked again every 5 minutes too. When today's map answers 404 (a tab left open across midnight, a collector that stopped), the page asks `/datenstand` at once, and the clamp moves the page to the day it names. A failed background request for `/datenstand` leaves a working map alone.
- **API fields.** `/datenstand`: `heute` (ISO day or null), `heute_stand` (the collector's `stand`, ISO UTC in whole seconds, or null) and `heute_stand_rest` (the rest source's `stand`). `/tageskarte` on today: `stand` and `bis_stunde` (live source), `stand_rest` and `bis_stunde_rest` (rest source), `deutschland_live` (true when the Germany card counts stations of the collector, false when it counts the rest source's), and per station `live` (true when its values come from the collector). `n`, `deutschland`, `deutschland_fern` and `deutschland_regional` cover the card's stations; `fehlende_stunden` is 0. A station without data has `n` 0, no punctuality, median or P90 (`ausfallquote` is a required number and reads 0), no normal and no class; the frontend goes by `n` = 0. On past days the new fields are null and `live` is false.

**Collector days** (the days between the last complete day and today, on Live-Lage only):

- **Which days.** The days in `data/live_tage.parquet` that lie after `letzter_tag` and before the current day in Germany. The collector writes a day there once it is finished ([pipeline.md](pipeline.md) §2, "Collector days"); it holds the large stations only, like everything on this page. A day in the monthly files or the raw days always wins: the collector's copy of it is ignored.
- **How they are served.** `/datenstand.live_tage` lists them, ascending, as ISO days. `/tageskarte` for such a day sums the file's hours per station and works like it does for a complete day: the same normal, classes, states and Germany card, no "vorläufig" label. `stand`, `bis_stunde` and `deutschland_live` are null, `fehlende_stunden` is 0 (the day table has no entry for the day; the collector's own check is the 12-hour rule), and the stations have `live` false.
- **Reference days across them.** A reference day after `letzter_tag` counts only if the collector kept it, for a collector day and for today alike, so the normals stay whole when uploads lag.
- **Germany and the states** count only the stations the collector kept that day, against the same stations on the reference days, as today's card counts only the reporting stations.
- **Kept for** 84 days, the 12 reference weeks.
- **The API picks the files up while it runs.** With `DATA_URL` set, the API downloads `heute.parquet` and `live_tage.parquet` at start when the blob container holds them, and checks them again at most once a minute from `/datenstand` and `/tageskarte`, with a conditional GET (`If-Modified-Since` is the modified time of the downloaded file, which is set to the blob's `Last-Modified`). A 404 means none and removes an old copy; any other failure keeps the old file and logs one line; a request that arrives while another one checks does not wait. The mtime-keyed caches pick the new files up. Without `DATA_URL` nothing is checked and the files are read from `data/`.
- **In the page.** `lageDays` in `frontend/src/api.ts` is the one rule: the newest day is today, else the newest collector day, else `letzter_tag`, and a day is selectable if it is today, complete or a collector day. The chips, the date field's upper limit and the clamp use it on Live-Lage; the Karte keeps `letzter_tag`. No new UI text.

**Normal.** The median of the same weekday over the previous 12 weeks, per metric, without days with missing hours and without nationwide public holidays. At least 8 valid days must remain, otherwise there is no normal. A day is valid for a metric only where the UI would show its value (the same low-data rule as the trend). The first weeks of the data have fewer than 8 reference days and read "kein Vergleich möglich".

## 3 Decisions

- **A delay histogram per day, not counters.** The day table keeps (`day`, `gruppe`, `eva`, `bucket`, `n`), the same shape as the month aggregate without weekday and hour. Reason: all four metrics, filters by category and station, and the median and P90 can only be computed from a histogram (see [patterns.md](patterns.md) §3); counters would give the punctual share and cancellation rate only. It costs about 36 MB over 27 months (measured on 2025-06 and 2026-09).
- **The day key is the planned arrival date** (Europe/Berlin). Reason: the same rule as weekday and hour in the month aggregate, so a day's counts and the heatmap agree.
- **Edge days are summed across month files.** A file holds the stops planned on the edge day of its neighbour month (the month comes from `time`, see [pipeline.md](pipeline.md) §3), so the same day can sit in two files. `combine` sums per key instead of dropping rows. Reason: measured on the real files, the overlap is tiny (0 and 1 stops repeated at two month boundaries), and summing is correct whether a stop is repeated or split.
- **Day gaps use the same `GAP_SHARE` rule as the months.** `day_gaps` counts the thin hours of the month's hour table per calendar day, so the days add up to the month's `missing_hours`. Reason: one definition of "incomplete" for the month and the day views.
- **The trend is a centred 28-day median over days without gaps and with enough data, with at least 14 values.** A day with little data is one whose value the UI would not show (the low-data rule of [app-shell.md](app-shell.md) §2). Reason: a median ignores single bad days (strikes, storms) and a gap day would pull the line down for a reason that is not the railway; a trend drawn from days that the same page dashes as too thin would break the rule that no value is shown below the limit; with fewer than 14 values the line would claim a trend from too little.
- **Days are the default view, months a switch.** Reason: the daily series is the richer view and was the point of the feature; months stay for the long run and for readers who want the earlier chart.
- **Line series and the station sparkline stay monthly until the line page.** Reason: per-line days need per-run data that the line detail page brings; the day table has no line key.
- **A separate route `/tagesverlauf` instead of a parameter on `/zeitverlauf`.** Reason: the monthly contract, its models and its tests stay unchanged, and the daily series has fields the monthly one does not (gap hours, trend) and no `linie`.
- **On Live-Lage, the normal is the median of the same weekday over the previous 12 weeks, without gap days and nationwide holidays, needing at least 8 valid days.** Reason: the same weekday removes the weekly rhythm, 12 weeks are recent enough to follow the timetable and long enough for a stable median, and holidays and gap days are not normal days. Fewer than 8 values would make the median depend on a few days.
- **The reference days reach back over the whole history; there is no cut at the full-coverage month.** Reason: Live-Lage lists only the 131 large stations, which the source covered over the whole history, so Germany's normal never mixes two station sets. The list of `referenztage` is what the Germany normal and the station normals rest on.
- **Live-Lage is its own page, not a mode of the Karte.** Reason: a Zeitraum | Tag switch on the Karte blurred where history ends and the live view starts; the Karte stays periods for all stations, and Live-Lage is the page for one day, today first. The product owner chose this and the position under "Entdecken" after the Karte ([app-shell.md](app-shell.md) §3).
- **Live-Lage lists only the 131 large stations.** Reason: they are the stations the source covered before full coverage, so every day since 2024-07 is consistent, and they have enough stops by morning. With all 5,000 stations most dots read "wenig Daten" on a morning, and the Fern view was nearly all grey.
- **The dots have no Gattung switch; Fern and Regional are secondary lines on the Germany card.** Reason: by morning a station has too few Fern stops for a dot, while the nationwide Fern and Regional values still rest on enough stops. The dots use all trains. The product owner chose this.
- **The partial raw day stays as the fallback for the 131.** Reason: a large station the collector has not completed yet (or a collector that is not running) would stay grey for hours although the source's raw data already holds its stops; before the DB key exists the page works from the raw data alone.
- **Rückblick: any day back to 2024-07 through the date field; each day is shown whole, against its normal.** An hour slider is not part of it (roadmap).
- **Three day chips (Heute, Gestern, Vorgestern); the date field reaches every other day.** Reason: the common question is "how was yesterday", which a chip answers in one click, and the field reaches the rest, so more buttons add little and crowd the filter bar on a phone. A chip whose day has no map stays, disabled with its reason, so the three places never move. The product owner chose this.
- **The Germany card is titled "Deutschland" on every day, and the freshness lines name the large stations.** Reason: both sources are limited to the 131 large stations, so "Alle Bahnhöfe" and "Übrige Bahnhöfe" were wrong, and a card titled "Große Bahnhöfe" on today but "Deutschland" on a past day of the same stations told two stories for one station set. The page lead already says that the page shows large stations. The product owner chose this.
- **The page leaves `g`, `von` and `bis` in the URL, untouched, and ignores them.** Reason: a link carries the query string, and dropping the Karte's Gattung and period on a visit to Live-Lage lost them for the way back. Its requests never send `gattung`, and the legend names all trains. The product owner chose this.
- **A station outside the 131 says so in the panel ("Die Live-Lage zeigt nur die großen Bahnhöfe.").** Reason: the Bahnhof chip and a station selected on the Karte reach any of the 5,000 stations, and the old text ("mit diesen Filtern") blamed filters that Live-Lage does not have and that cannot bring the station back.
- **`/tageskarte` takes no `gattung` and serves only the large stations.** Reason: no page asks for another selection any more, and one set of stations keeps the cache entries small and the reference scan short. The category appears as `deutschland_fern` and `deutschland_regional`.
- **Without `tag` the URL is the newest day; a past day sets `tag`; the chip of the newest day removes it.** Reason: a bookmark or a link to `/lage` always opens live, and a link to a past day is shareable. The key is `tag` because the existing filter keys are German and short (`von`, `bis`, `gattung`).
- **Live-Lage shows the deviation from the normal on a five-step diverging scale.** Reason: the question of a day map is "worse than usual?", not "how punctual?", and a station that is always late must not look like a bad day.
- **"Better or worse than usual" is noise-aware: a station's step comes from z, its deviation from its normal divided by the spread of its own reference days.** The spread is 1.4826 times the median absolute deviation (a robust standard deviation) with a floor per metric (1 pp punctuality, 0.5 pp cancellation rate, 1.5 min median and P90); |z| below 1 is as usual, 1 up to 2 better or worse, 2 and more much better or much worse. Reason: narrow bands, because with wider ones most state-days read as usual and a day that is clearly off barely showed; fixed bounds of a few percentage points or minutes, the same for every station, sat below a small station's daily noise and coloured three quarters of the map on an ordinary day. Measured on 2026-09-08, -15 and -16 with the earlier bands of 2 and 4 spreads: "as usual" went from 25 % to 75 to 84 % for punctuality and to 87 to 92 % for the median (§5). With the bands of 1 and 2 spreads, punctuality on the state-days reads 58 % as usual, 25 % better or worse and 16 % much better or much worse. The product owner chose this.
- **The class is computed in the API, the frontend only maps it to a colour.** Reason: one rule, testable in pytest. A station has no class without a shown value or without 8 shown reference days.
- **The floor for the median and P90 is 1.5 min.** Reason: the stored values are whole minutes, so one rounding step must not change the colour. With a floor of 1 min and the bands of 1 and 2 spreads, a stable normal turned every one-minute change into "better" or "worse" (measured on 2026-09-08, -15 and -16: only 60 to 69 % of the stations read "as usual" for the median, 61 to 64 % for P90, and "much better" never occurred). At 1.5 min a minute off reads as usual, 2 minutes as a bit better or worse, 3 minutes as much. With a floor of half a minute the median also leaned toward "worse". The product owner chose this.
- **Germany, Fern, Regional and every state get a class by the station rule, and their cards show the step colour and the deviation number.** The pooled value of an area is compared with the area's own reference days (the same days, spread, floors and `shown(...)` rule as a station), and the card reads "value − usual" in the metric's unit on the step colour. Reason: one visual language for the dots, the states and Germany, so a colour means the same everywhere and a reader needs to learn nothing new. An earlier version drew five weather symbols from the rank among the reference days; the product owner found them confusing and chose the step and the number. The card follows the selected metric.
- **Without a class a card shows "–", not a number.** Reason: "kein Vergleich möglich" means there is no deviation to show (too few reference days, a gap day, too few stops), and a number next to a grey block would invite a comparison the rule does not support.
- **A gap day gets no class for Germany or the states.** Reason: the same one that keeps gap days out of the trend: a day with missing hours would be compared with complete days, and the gap, not the railway, could be the reason. The grey card names it. The product owner chose this; the stations keep their steps.
- **`days.parquet` has row groups of about one day (50,000 rows).** Reason: a one-day filter then skips the other groups. Without it, every distinct day queried grew the process, because Polars scanned all 24.5 M rows (§5). Statistics are Polars' default, the data is sorted by day, so a group covers about 1.7 days on average.
- **The cell statistics of `/tageskarte` are vectorised** (`cell_stats_frame` in `core/stats.py`, one sort and one group-by instead of a Python loop per cell). Reason: cold time (§5). `cell_stats` stays the definition: an equivalence test over 405 cells (`test_cell_stats_frame_equals_cell_stats`) compares both exactly.
- **The date field writes only complete days inside the data.** Reason: typing a year passed through `0002-09-15` and `0020-09-15`, which the clamp moved to the first data day mid-typing, each with a cold request. The field is uncontrolled and follows the URL only when the URL's day changes, because a controlled field reset its segments after every ignored half-typed value.
- **Labels follow the loaded day.** Reason: with the previous day's data still on screen during a day switch, the panel read "Di., 15.09.2026" next to Monday's values.
- **Bundesländer are the middle level between Germany and the stations.** Reason: everyone knows them, the states order regional trains, and each of the 131 stations carries its state from Wikidata already. Considered and left out: the seven DB network regions (little known by name), rail hubs (not a partition of the map), corridors or lines (a train crosses several) and clusters computed from the data (nothing a reader can name). The product owner chose the Bundesländer.
- **The state shapes are Natural Earth polygons in one small static file, `frontend/public/laender.geojson` (35 KB), not the base map's tiles.** Reason: the first version drew the tiles' `boundary` lines, which gave lines only: no wash outside Germany and no area to hover or click, and whether the lines exist at the overview zoom depends on the base style. Polygons give the wash and the areas, the file is public domain (Natural Earth needs no attribution), it is fetched from the site's own origin (the CSP needs no change) and it follows the theme through tokens. It was cut once with mapshaper, which is not a project dependency (§4). The product owner chose this after the first test round.
- **All 16 states get a card, each naming its station count.** Reason: a map with holes would read as missing data, and the count tells the reader what the card rests on: Bremen, Saarland and Mecklenburg-Vorpommern have one large station, Sachsen-Anhalt and Thüringen two (§8). A state is compared with its own reference days, so a small state is not measured against a big one.
- **Below 768 px a state card shows the number only.** Reason: with the unit the 16 cards overlapped at 375 px; the unit stays in the card's name, the tooltip and the page card.
- **The text on a step colour has its own tokens (`--on-r1` to `--on-r5`, `--on-c3`), at least 4.5:1 in both themes.** Reason: white on the light steps and dark on the others cannot come from one text token, and the cards carry the number as text.
- **At the overview the state is the target: the dots are very faint (20 %), inert, and a hover or click on a state's area or card picks the state. Zooming in swaps the cards for the full dots.** Reason: at the overview 131 dots at full strength compete with the cards; faint, they still show where the stations are, and one target per gesture (the state) keeps the overview predictable. Past the detail zoom the areas fade out and the dots take the interaction as before. The product owner chose this.
- **The state is the URL key `land`.** Reason: a link to a state's card is shareable and a reload keeps it, like `tag`. The key is the code, not the name, so it does not depend on the language.
- **The count is distinct station names, not EVAs.** Reason: Berlin's large stations are split into 23 EVAs under 11 names, and "23 große Bahnhöfe" would be wrong for a reader.

Today:

- **Today has two sources: the collector for the large stations, the partial raw day as the fallback for the same stations.** Reason: the scope of [adr/0002-live-source.md](adr/0002-live-source.md), within the documented 60 requests a minute. The rest needs no DB key, so today works at the source's freshness before the key exists.
- **The cut is the last full hour, today and on the reference days alike.** Reason: stops planned in the current hour are still running, and without their change data they would count as on time; cutting the reference days at the same hour compares like with like. The product owner chose this.
- **On today the Germany card counts the stations that report today, against the same stations and hours.** Reason: the same stations on the reference days keep the comparison fair, each cut at the hour of its own source. Where no station reports yet, the card counts the rest source's stations instead. Reason: the card and the map would otherwise be empty while the rest source has data.
- **An open tab asks for today again every 5 minutes.** Reason: the collector runs every 15 minutes, so a new run shows within 5 minutes at small cost. The product owner chose this. Only today is polled; past days are not.
- **`/datenstand` is polled only while it names a today.** Reason: a tab that stays in front never refocuses, so without the poll the end of today (a stopped collector, midnight) would end in the error banner. On Azure there is never a today, and polling there would wake the API from scale to zero for every open tab.
- **A 404 for today asks `/datenstand` at once.** Reason: a tab left open across midnight would otherwise show the error banner until the next poll.
- **A day after the last complete one that is not served moves to the newest day.** Reason: a day between `letzter_tag` and today may have no data (the raw day is not complete yet, the collector did not keep it), and the field offers it; the map shows the newest day instead of an error.
- **The collector fetches the slices before the cut station by station, after the changes of every station, then the hours ahead.** Reason: a station counts only once all its slices before the cut are in. Nearest hour first over all stations kept the whole map grey through a first run's catch-up and then showed every station at once; station by station, about 42 stations become ready per run.
- **A 12-minute deadline per run instead of a request budget.** Reason: a fixed number of requests did not bound the wall time (latency, 30-second timeouts), so runs every 15 minutes could overlap, add up to more than 60 requests a minute and overwrite each other's state. The deadline runs on the injected clock, so it is testable.
- **A station counts only when its changes came in the same collector run or raw pass.** Reason: without this run's `fchg` its planned stops merge as on time, and a fresh `stand` would hide a failed run (network down, key blocked). When every request fails, the collector's file is empty and the map falls back. For the rest file the same rule keeps only the stations that answered with a body in the newest `fchg` pass.
- **`stand` is the start of the run or pass.** Reason: the changes are fetched first, so the start is the time of the data. The end of a run that crossed an hour gave a cut one hour after the rows, and a run across midnight a cut of 0 with no reference hours at all.
- **The live source counts while under 2 hours old, the rest source while it is of the local date.** Reason: a collector that stopped must not show an old morning as today; the rest is up to about 10 hours behind by nature, so an age limit would hide it most of the day. Both must be the local date of now and after `letzter_tag`, so yesterday's young file is no "today" just after midnight.
- **`day_hours.parquet` and `large.parquet` are downloaded on deploy; `heute.parquet` and `live_tage.parquet` are fetched when present.** Reason: today and the collector's days need the hour table and the set of large stations wherever a live file exists, and the 24.9 MB hour table lengthens a cold start only slightly. The two live files are optional because they appear and change while the API runs. `heute_rest.parquet` is never downloaded: it comes from the raw data, which the deployment does not have.
- **The partial day is written last by `pipeline.update`, as one file, not as a day folder.** Reason: `combine` and the complete-day logic stay untouched, and a failing download of today's raw files never keeps the complete days from being combined.
- **On today the large stations with coordinates that no source covers yet are listed as `n` = 0.** Reason: on today such a station means "not yet", not "no trains", and the map stays whole while the sources fill.
- **Every `stand` is sent in whole seconds.** Reason: JavaScript engines differ in parsing fractional seconds beyond three digits.
- **Local time comes from Polars** (`core.periods.local_time`, and `local_midnight_utc` for the other direction). Reason: Windows has no `tzdata`, and Polars already carries the time zone rules, so no package is added; the collector, the raw days and the API share these functions.

Collector days:

- **The collector keeps its own finished days.** Reason: the complete days end at the last `pipeline.update`, and a deployment gets new data only when the product owner uploads it; the collector already sees every change of the day, so yesterday can be there without waiting for that. The product owner chose this.
- **A collector day has no "vorläufig" label.** Reason: measured on 7 October days, a day folded with the first complete run after local midnight equals the day settled by the morning run: Germany within 0.01 %-points, the same Germany class, at most one station class changed of the 131 ([pipeline.md](pipeline.md) §3).
- **A complete day wins over the collector's copy.** Reason: the monthly files and raw days are the checked source, so one rule decides which numbers a day shows, and `/tageskarte` for a day up to `letzter_tag` never reads the collector file.
- **From local midnight on every run also folds its changes into yesterday, and the first run from 01:00 finalizes it.** Reason: the changes of the night (`fchg` reaches back 13 to 14 hours) belong to yesterday's last stops; the runs already hold them, so it costs no request. The runs of the first hour of the new day only add changes.
- **A day is dropped when two answered runs, or its local midnight and the first run, lie more than 12 hours apart.** Reason: `fchg` reaches only 13 to 14 hours back, so changes in between were never seen and the stops would count as on time (a collector that started at 20:00 would otherwise keep a day whose early stops are all on time). The check starts at the local midnight, and the runs between 00:00 and the finalizing run count for yesterday too. A dropped day is marked finished and not tried again.
- **A station counts only with all 24 plan slices of the day and changes from the finalizing run.** Reason: the rule of today's stations; without that run's `fchg` a station's planned stops would all look on time.
- **A run that was cut short (HTTP 429, the deadline) or got no changes does not finalize.** Reason: a throttled run at 01:05 would freeze the day with three stations; the next run finalizes it.
- **The file keeps 84 days (`KEEP_DAYS` = 7 × `WEEKS` of `core.normal`).** Reason: the same weekday of every reference week stays available however long uploads lag; about 2.5 MB. A shorter window thinned the normals after about nine weeks without an upload.
- **The API checks the live files from the request path, not from a background thread.** Reason: standard library only, no timer to stop, and it costs nothing while nobody asks; at most one conditional request a minute, and a request never waits for it.

## 4 Architecture and data keys

- `core/holidays.py`: `nationwide_holidays(year)` returns the nine nationwide dates as a `frozenset[date]`: New Year, Good Friday, Easter Monday, 1 May, Ascension, Whit Monday, 3 October and both Christmas days. Easter comes from the anonymous Gregorian algorithm, no library.
- `pipeline/aggregate.py`: `days` builds the per-day histogram of a month file, `day_gaps` the missing hours per calendar day; both reuse `_hour_counts`, which `meta` uses too and which calls `hour_table`, the one gap rule that the raw days use as well ([pipeline.md](pipeline.md) §3). `pipeline/update.py` lists them in `MONTH_FILES`; `combine` writes `data/days.parquet` and `data/tage.parquet` ([pipeline.md](pipeline.md) §2).
- `data/days.parquet`: `day`, `gruppe`, `eva`, `bucket`, `n`, sorted by day, EVA, group and bucket (NULL bucket = cancelled stop, never 0 minutes), written in row groups of `DAYS_ROW_GROUP` = 50,000 rows ([pipeline.md](pipeline.md) §2). `data/tage.parquet`: `day`, `missing_hours`, one row per calendar day up to the last complete day. Both include the raw days after the last monthly file.
- `backend/main.py`: `GET /tagesverlauf` (`eva`, `gattung`) returns `titel` and `tage` (`tag`, `n`, the four statistics, `fehlende_stunden`, `trend`); `trends` computes the centred median with `rolling_median_by`, and `tage_for` caches per selection and file modification times. `/datenstand` carries `erster_tag`, `letzter_tag` and `fehlende_stunden_tage`. The paths are `DAYS_PATH` and `TAGE_PATH`, both in the deploy download list ([patterns.md](patterns.md) §2 and §4, [deployment.md](deployment.md)).
- `core/normal.py` (pure, no framework imports): `reference_days(day, first, last, gap_days)` lists the same weekday of the previous 12 weeks, nearest first, without days outside the data, gap days and nationwide holidays. `normal(values)` is the median, `None` below 8 values.
  - `spread(values, floor)` is 1.4826 times the median absolute deviation from the median, at least `floor`, `None` below 8 values. `deviation_class(value, references, higher_is_better, floor)` is the step 1 to 5 from z (`USUAL_Z` 1, `MUCH_Z` 2); `None` without a value or a normal. `FLOORS` is the one table of the floors per metric, in the metric's own unit. `core/rankings.py` has `higher_is_better(metric)`, the one place that says only punctuality counts higher as better.
- `core/stats.py`: `cell_stats_frame(lf, keys)` computes the statistics of every (keys) cell of a (keys, bucket, n) frame in Polars: a running count of arrived stops per cell, then the smallest bucket with `cum >= q * arrived` as median and P90. It needs one row per (keys, bucket) and key columns without NULLs.
- `core/periods.py`: `large_stations(days, full_start)` is the one rule for the large stations: the EVAs with stops in the last month before the full-coverage start, read from `days.parquet`. The collector (`pipeline/live.py`) and the API both call it, so the set is the same everywhere. The API calls it on `DAYS_PATH`, which is deployed, so the Rückblick works on Azure too; the result is cached by file modification times like the other caches.
- `backend/main.py`: `GET /tageskarte` (`tag` as `YYYY-MM-DD`; no `gattung`) returns the `Tageskarte`: `tag`, `referenztage` (nearest first), `fehlende_stunden`, `deutschland` (all trains), `deutschland_fern`, `deutschland_regional` (each a `Deutschland` or `None`), `n`, `ohne_koordinaten` and `stationen`, all for the large stations only. A malformed or impossible date is 422, a day outside `tage.parquet` 404.
  - `TageskartenStation` is the `/karte` station (`KartenStation`, built by the join `/karte` shares) plus `normal` and `klasse`. `Deutschland` is the day's four statistics plus `normal` and `klasse`, for Germany, for Fern and Regional (the same grouping by `gruppe`) and for each state. `Normal` holds `puenktlich`, `ausfallquote`, `median` and `p90`, each `None` without a normal; `Klasse` holds the same four as the step 1 to 5, or `None`. Only `puenktlich` counts higher as better.
  - `deutschland` is `None` (with `n` 0 and no stations) when the large stations have no stops that day; `deutschland_fern` and `deutschland_regional` are `None` without stops of their category. Only stations with coordinates are listed; `ohne_koordinaten` counts the others. On a day with missing hours the `klasse` of Germany, Fern, Regional and every state is `None` for every metric; the stations' `klasse` stays.
  - A value feeds a normal or a step only where `shown(...)` holds, the rule the trend feed uses (at least 15 stops for the cancellation rate, enough arrived stops for the delay metrics). `counting` and `references_of` collect those values once per station and per area. The day's own value gets a step only when it is shown too. A station's step needs 8 shown reference days.
  - The reference window starts at the first data day. The full-coverage start, which fixes the set of large stations, comes from `monate.parquet`, so that file's modification time is part of the cache key.
  - `tageskarte_for` reads `days.parquet` for the day and its reference days only (a `is_between` prefilter lets Polars skip row groups), groups to (day, station, bucket), and computes the statistics per (day, station) with `cell_stats_frame`; it is cached per process ([patterns.md](patterns.md) §8). The response is gzip-compressed.
- `frontend/src/AreaCard.tsx`: `AreaCard`, the page card for Germany or one state, `Step` (the deviation on the step colour, `role="img"` with its label) and `stepOf`, `figures`, `stationCount` and `stateTip`, which the state cards use too. `frontend/src/metrics.ts`: `tag` and `land` in `Filters`, `readFilters` and `writeFilters`; `API_FIELD` (metric to API field, the one map the trend and the rankings use too), `display`, `REFERENCE_WEEKS`, `figureText`, `deviation` (the API's step and the normal as text, `null` where there is nothing to compare) and `offsetText` (value minus normal, rounded like the metric, with "+", "−" or "±" and the unit `unit.min` or `unit.pp`; cancellations get one decimal). `frontend/src/MapPage.tsx` is one component for both map pages: it takes a `day` prop, `/karte` renders it without and `/lage` with, and it holds the second query, the day colouring, the legend and the panel lines; `frontend/src/Filters.tsx` the date field and the chip strip. A failed `/datenstand` shows the error banner on Live-Lage instead of loading for ever.
- Bundesländer: `core.stations.LAND_CODES` maps the 16 Wikidata labels of `data/stations.parquet`'s `land` to lower-case codes (`bw`, `by`, `be`, `bb`, `hb`, `hh`, `he`, `mv`, `ni`, `nw`, `rp`, `sl`, `sn`, `st`, `sh`, `th`); a label outside the table gets no code. In `tageskarte_for` the nation rows join the station names and codes and are counted twice, once as area `de` and once per state, so the cells are keyed by (day, area, gruppe) and `area(code, gruppe)` builds the `Deutschland` of Germany and of each state with the same `references_of`, `normal_of` and `klasse_of` as a station (and no class on a gap day). `bahnhoefe` counts distinct names per state among the day's rows.
- `frontend/src/laender.ts`: `ANCHORS`, the hand-placed [lon, lat] of each state's card, and `landName(code)`. `frontend/src/StateMarkers.tsx`: one MapLibre marker for each of the 16 states, built once while the cards show, with a button rendered into it by a React portal (step block, name, tooltip, click, hover and focus tint). In `frontend/src/MapPage.tsx`, only on Live-Lage, the map fetches `laender.geojson` once (relative to `BASE_URL`, kept in the effect's closure; a failed fetch leaves the cards working without areas) and the `style.load` hook adds it as the source `laender` (`promoteId: "code"`) with four layers below the base map's first label layer and so below the dots: `mask` (the wash, token `--mask` at 0.6), `laender` (a transparent fill per state whose feature-state `hover` tints it with `--accent` at the opacity `--tint`, 0.14 in the light and 0.3 in the dark theme, read when the layer is added so a theme switch picks it up), `laender-line` (`--state-line`, 0.8 px) and `de-edge` (the mask's outline, which is Germany's border, `--text-3`, 1.5 px). `fadeAreas` fades the mask and both lines from the detail zoom (`detailAt`: the start zoom plus one, or while a state is picked the lower of that and the state's fit zoom, `stateZoom`) to zoom 8 and is moved whenever the start view is refitted or a state is fitted. One `zoom` listener sets `detail`; `FADED` (0.2) multiplies the dots' own opacity at the overview, where the dot handlers return early and the `laender` layer's `mousemove` and `click` handlers show the state's tooltip and pick it; an effect fits the picked state's shape (`shapeBounds`; it waits until `laender.geojson` has loaded or failed, and on failure uses the state's stations, else its card's anchor), caps at `STATE_ZOOM` 8, remembers the fit zoom as `stateZoom`, fits again on a new pick of the same state (a counter), and back to Germany. A `moveend` listener writes the camera into the attributes `data-zoom` and `data-bounds` (west, south, east, north) of the map element, which the tests read. `padding()` takes the bottom card stack on Live-Lage, and the `ResizeObserver` that watches the filter card watches the stack too. `land` is a `Filters` key in `frontend/src/metrics.ts`; MapPage keeps it only on `/lage`, and the other pages set it to `undefined` next to `tag`. State names are the keys `land.<code>` in both catalogs.
- `frontend/public/laender.geojson` (35 KB): the 16 states, each feature with a `code` (the lower-case ISO 3166-2 code), plus one feature `mask`, a large rectangle with Germany cut out. It is Natural Earth 10m admin-1 data (public domain), cut and simplified once, and is excluded from Prettier (`frontend/.prettierignore`). To rebuild it, download `https://naciscdn.org/naturalearth/10m/cultural/ne_10m_admin_1_states_provinces.zip`, unpack it into an empty folder and run there (mapshaper is not a project dependency):

  ```
  npx mapshaper@0.7.101 -i ne_10m_admin_1_states_provinces.shp -filter "iso_a2 == 'DE'" -each "code = iso_3166_2.slice(3).toLowerCase()" -filter-fields code -simplify 20% keep-shapes -rename-layers states -dissolve + name=de -rectangle bbox=-20,30,45,70 name=world -erase de target=world -each "code = 'mask'" target=world -merge-layers target=states,world force name=laender -o laender.geojson precision=0.001 format=geojson
  ```

  Then copy the result over the file and check the 16 codes and the `mask` feature.
- `frontend/src/ZeitverlaufPage.tsx`: the page with the Tag/Monat switch, the day and month rows and the table mode. `frontend/src/charts.tsx`: the chart pieces both resolutions share (`Plot`, `Line`, `TrendLine`, `Band`, `Markers`, `tipOf`). `frontend/src/metrics.ts`: `readFilters` and `writeFilters` carry `z`. The shell around it is in [app-shell.md](app-shell.md).
- Frontend keys: the daily series is the default of `/muster/zeitverlauf`, `z=monat` switches to months and is dropped on every other page; a line URL drops `z`, stays monthly and hides the switch; `tag` is the day of `/lage` and is dropped on every other page, the Karte included; `land` is the state of `/lage` and is dropped the same way.

Today:

- `data/day_hours.parquet`: `day`, `hour` (Int8, the planned arrival hour), `gruppe`, `eva`, `bucket`, `n`, sorted by day, hour, EVA, group and bucket, in row groups of `DAYS_ROW_GROUP`. `pipeline.aggregate.day_hours` is `days` with the hour in the keys (both through `_per_day`), so summed over the hour it is `days.parquet` for the large stations. Month and raw-day folders carry the table for every station; `combine` sums it like `days` and keeps only the large stations in `data/day_hours.parquet`, because today lists no others ([pipeline.md](pipeline.md) §2).
- `data/heute.parquet` (the collector) and `data/heute_rest.parquet` (the partial raw day): the `day_hours` shape for the large stations' hours before the cut, plus a constant column `stand` (`Datetime("us", "UTC")`). Both are written to a `.tmp` sibling and renamed. Zero rows mean "nothing for today": before 01:00, when no station is ready, or when the newest raw pass is from yesterday.
- `data/live/YYYY-MM-DD/`, the collector's state for one local day: `plan.parquet` (the `plan` stops, `PLAN_COLUMNS`), `fchg.parquet` (the merged change stops, `FCHG_COLUMNS`) and `slices.parquet` (`eva`, `hour`: the fetched `plan` slices) and `runs.parquet` (`t0`, naive UTC: the start of each run that got at least one answer; a run between 00:00 and the finalizing run is recorded in yesterday's folder too). The empty file `final` marks a day that was kept or given up. The XML is parsed and dropped. Folders older than yesterday are deleted; a run reads yesterday's folder only while it has no `final`.
- `data/live_tage.parquet`: the collector's finished days in the shape of `day_hours.parquet` (`day`, `hour`, `gruppe`, `eva`, `bucket`, `n`), sorted, written to a `.tmp` sibling and renamed. `data/large.parquet`: `eva`, the large stations ([pipeline.md](pipeline.md) §2).
- `pipeline/live.py`: `run(data_dir, get, now, sleep)` is one run with the HTTP call and the clock injected; `large_evas` reads `data/large.parquet`, which `pipeline.update.write_large` writes by `core.periods.large_stations` (`combine` and `update_rest` keep only these stations in `day_hours.parquet` and `heute_rest.parquet`); `_finalize` writes a finished day; `main` reads `DB_CLIENT_ID` and `DB_API_KEY` (stripped; exits naming both when one is missing) and calls the API with `urllib`. Constants: `PACE` 1 s, `DEADLINE` 12 min, `AHEAD` 3 h, `TIMEOUT` 30 s, `FINAL_HOUR` 1, `MAX_RUN_GAP` 12 h, `KEEP_DAYS` 84. It folds the responses with `pipeline.raw.parse` and turns them into stops with `merge`, the two steps of `stop_rows`.
- `pipeline/update.py`: `update_rest(data_dir, raw, now, large)` writes `heute_rest.parquet` for the large stations after `combine`; `newest_fchg(raw, keys)` finds the newest file with a `fchg` snapshot, for `update_rest`; `day_complete(raw, keys, day)` is the completeness rule of the raw days (a complete run after local midnight, [pipeline.md](pipeline.md) §3). `pipeline/raw.py`: `fchg_pass(path)` returns a raw file's pass start and the stations that answered with a body; `RawSource.fchg_span(key)` returns a file's first and last `fchg` request time and their number.
- `core/periods.py`: `local_time(t)` turns an aware instant into the naive Europe/Berlin time of the source's clock. The local day and the cut of both sources and the API's "today" come from it. `local_midnight_utc(day)` is the start of a local day as naive UTC (daylight saving included), for the completeness rule and the collector's gap check.
- `backend/main.py`: `DAY_HOURS_PATH`, `HEUTE_PATH`, `HEUTE_REST_PATH`, `LIVE_TAGE_PATH` and `LARGE_PATH` (defaults `data/<name>.parquet`); `DAY_HOURS_PATH` and `LARGE_PATH` are in `DATA_FILES`, the others are not. `live_tage()` lists the collector's days after `letzter_tag` and before today, `refresh()` calls `fetch.refresh_live` for the two live files (first thing in `/datenstand` and `/tageskarte`), `large()` reads `LARGE_PATH` and computes the set from `days.parquet` only where that file is missing. `Datenstand.live_tage` is the list of ISO days. In `tageskarte_for` the reference days reach the last collector day, a collector day's hours come from `LIVE_TAGE_PATH` summed over the hour (unless the day is today), and the file's modification time is in the cache key of today and of the collector days only, so complete days keep their entries while the collector runs. `backend/fetch.py`: `_copy` (to a `.part` file, modified time set to the blob's `Last-Modified`, then renamed), `_sync` (one conditional GET), `refresh_live` (`COOLDOWN` 60 s, `REFRESH_TIMEOUT` 10 s, a non-blocking lock). `today_sources()` returns `(live, rest)`, each a `Heute` (day, `stand`, cut, the file's modification time and its rows) or None, by the rules in §2 (`HEUTE_MAX_AGE` 2 h for the live file); `_heute_for` caches a file per path and modification time, and each file is stat'ed and read once per request. `/tageskarte` for today runs `tageskarte_for` on `day_hours.parquet` with both sources in the cache key, so a new run is a new entry while past days keep theirs.
- Frontend: `LIVE_REFRESH` (5 min) and `lageDays` in `frontend/src/api.ts`, used by `useDatenstand` and the day map query; the clamp, the 404 refetch and the per-source labels in `frontend/src/MapPage.tsx`; the chip strip in `frontend/src/Filters.tsx`; `today` of `AreaCard` in `frontend/src/AreaCard.tsx`; `formatStand` and `formatLive` in `frontend/src/metrics.ts` (times in Europe/Berlin, 24 h). The e2e fixtures `datenstandHeute(sources)` and `heuteKarte(sources)` in `frontend/e2e/fixtures.ts` cover live only, rest only and both.

## 8 Known shortcuts

- Regional public holidays (Epiphany, Corpus Christi and others) are left out of `core/holidays.py`. A regional holiday can therefore sit among the reference days of a normal.
- Day gaps are counted by the day of the poll time, while the day key of the histogram is the planned arrival. A gap around midnight can mark the neighbouring day.
- `tage_for` keeps the computed series per process (`lru_cache`, 16 entries, keyed by selection and both file modification times), like the other caches ([patterns.md](patterns.md) §8). The first request of a selection computes it: 1.6 s nationwide, 0.7 to 0.8 s for one station or `gattung=fern`, about 30 ms afterwards (measured, §5). An entry is one model per day. Revisit when the station page is used heavily or the days outgrow this.
- The nationwide trend around the start of full coverage (2025-11) blends two populations: about 135 stations before, all stations after, for roughly two weeks on each side of the change, because the window is centred. The "Datenbasis erweitert" marker explains the step; the monthly series has the same step. Not fixed. Resetting the rolling window at `vollabdeckung_ab` would remove it.
- `tageskarte_for` keeps the computed day per process (`lru_cache`, `maxsize=16`, so the last few days stay warm, keyed by the data files' modification times, the sources of today and the day). An entry is a model with one object per large station: about 0.35 MB of Python objects, against about 10 MB when it listed every station. Measured on the large stations: a cold day takes 0.04 to 0.16 s, twenty distinct days settle at a working set of about 310 MB (172 MB idle). The 420 MB, 580 MB peak and 2.4 s of §5 were measured with all stations. Revisit when memory or cold time grows; the next lever is `shown`, `thin` and the normal in Polars, which would split the one rule.
- `days.parquet`'s row groups (`DAYS_ROW_GROUP`) are about one day only on average: 491 groups over 822 days, and 387 of them span more than one day, because early days have far fewer rows than the 30,000 average. A one-day filter reads one or two groups. A smaller constant is one line if memory asks for it.
- No test reads the row groups: neither Polars nor an installed library exposes them. A test with a hand-written footer reader was dropped; the evidence is the memory measurement in §5. If pyarrow becomes a dependency, a test of `pq.ParquetFile(...).metadata` is short.
- Nothing cross-checks that the API gives no class where the UI would call the value low: the API's `shown(...)` and the UI's `show()` are two implementations of the same rule, and Live-Lage no longer asks `show()` before colouring. They agree while both keep that rule.
- On a screen about 720 px high the Germany card and the open legend cover a few dots at the western edge. A taller screen is fine; the period map's legend alone nearly did that already.
- At the end of the series the centred window shrinks to a trailing one over the last 14 days and still needs 14 values, so the trend reaches the newest day only while the last 14 days all feed it; every gap or thin day among them cuts one day off its tail. With the raw days and no gap in October it reaches the newest day. Allowing half the minimum in the windows that run past the last day would keep it there, at the price of a lagging trailing median.
- The trend is the median of the days that pass the low-data rule, per metric. A station whose days all have little data therefore has no trend line, although its days are still drawn.

Today:

- **A first run of the day catches up over several runs** (`ponytail:` at `DEADLINE` in `pipeline/live.py`). A run makes at most 720 requests, 589 slices after the 131 changes; at 14:00 the slices before the cut are 131 × 14, so about 42 stations become ready per run, all of them in the fourth run and the slices ahead in the fifth. This assumes DB answers at once. A higher quota from DB (a smaller `PACE`) shortens it.
- **The large stations are frozen** to the last month before full coverage (`ponytail:` in `core.periods.large_stations`): 131 EVAs from 2025-10. A new large station needs a rule beyond the old source.
- **Three states rest on one large station and two on two** (Bremen, Saarland and Mecklenburg-Vorpommern; Sachsen-Anhalt and Thüringen). Their card is those stations' day, not the state's. The card names the count ("1 großer Bahnhof"); there is no minimum, and a full station set behind the level would need the all-station day table.
- **The state cards sit at hand-placed anchor points** (`ANCHORS` in `frontend/src/laender.ts`), not at the states' centres, so that Berlin and Brandenburg, Bremen and Niedersachsen, Hamburg and Schleswig-Holstein and the Saarland and Rheinland-Pfalz do not overlap at 375 × 812. A card can therefore sit off its state's middle.
- **Shorter phones overlap state cards** (accepted by the product owner). The start view keeps clear of the bottom cards, so on a phone Germany gets smaller as the screen gets shorter: at 375 × 812 the 16 cards stay apart (tested, also with every state compared), on shorter screens some touch. A compact phone card or other anchors would lower the limit.
- **The state areas are simplified Natural Earth shapes** (10m admin-1 data cut to 20 % of its points, 0.001° precision, §4). They are good at the overview and rough at higher zoom, so the wash and the lines fade out between the detail zoom and zoom 8, where the base map's own borders take over; the two sets of lines are not the same geometry. A sharper edge at higher zoom would need a less simplified file (more KB) or the base map's own boundary layer.
- **A state's fit uses the simplified Natural Earth shape**, so the view is as exact as that file. If the shapes fail to load, the fit falls back to the state's stations (or its card's anchor if it has none that day) and may cut parts of the state. The fit waits for that fetch, so one that never settles leaves a state click without a zoom; for a 35 KB static file that is accepted.
- **The collector's state is reread and rewritten whole on every run** (`ponytail:` in `run`), a few MB. Append per run if the runs get slow on the VPS.
- **Every `pipeline.update` downloads today's two UTC folders again** (`ponytail:` in `update_rest`), about 2 × 160 MB. Keep them in a local cache if updates run often.
- **About 290 stations answer piebro's `fchg` pass with an empty body** (ADR 0002), so they drop out of the rest file. Most of them are stations without trains; a large station among them that the collector has not completed yet draws grey on today.
- **A station whose `fchg` failed in the finalizing run is lost for the day** (`ponytail:` in `_finalize`), even when it answered in the runs since midnight, which carry the same changes. The next run could still add it, at the price of keeping the day open for hours. About 0 to 1 station a day at a 0.5 % error rate.
- **A collector day has no gap hours.** `fehlende_stunden` is 0 for it; the 12-hour rule between runs is the only check, so a quiet hour in the source's data would not show as a gap.
- **A station that never completes its slices** (for example empty `plan` bodies) asks for its missing slices again on every run and stays grey; the API cannot tell it from a complete station without arrivals. Hours without trains answer with an empty timetable and status 200, so they count as fetched.
- **The collector reads `data/large.parquet`** and exits naming `pipeline.update` when it is missing. It does not need the `pipeline` group (the download library is imported only by the raw source), but the API image does not contain `pipeline/` (§6).
- **Live and later monthly values come from different collectors**, so a day can shift a little when the raw days and then the monthly file replace it; today is never stored as a day.
