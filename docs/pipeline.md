# Pipeline

## 1 Overview

Turns the monthly source files from `piebro/deutsche-bahn-data` into compact tables: a delay histogram (weekday × hour × category × station × month), a station table with names, stop counts and coordinates, line histograms per month, a delay histogram per day, a line table, the delay changes between consecutive stops of a line with its station order, the stops of every trip with their times (the last 28 days of them in one file for the line page's Bildfahrplan), a stop count per station, a trip count per line and a delay histogram per line, weekday and hour (the record rankings and the line heatmap, [patterns.md](patterns.md)), a month table with coverage figures and a day table with the hours missing per day. Each month is processed once into its own folder; a combine step then writes the files the API reads. Raw data stays local.

The current month, which has no monthly file yet, is covered for the day views only: the days after the last monthly file are built from the source's raw Timetables responses, up to the last complete day (§2, "Raw days"). The month views never use them.

Today so far comes from two places: `pipeline.update` writes the current day from the raw responses as far as they reach (§2, "Today so far"), and the collector `pipeline.live` asks the DB Timetables API for the large stations every 15 minutes (§2, "Live collector"). An hour table (the day histogram per planned arrival hour) lets the API cut the reference days at the hour today has reached. How the map uses them is in [day-history.md](day-history.md).

## 2 Spec

Commands (from the repo root):

- `uv run python -m pipeline.coords` runs one SPARQL query against Wikidata and writes `data/coords.parquet`. Needs network access. `pipeline.update` runs it on the first run when the file is missing, and never refreshes an existing file, so run this command to refresh the coordinates.
- `uv run python -m pipeline.update` is the one command for the data. It lists the monthly files on HuggingFace, downloads and processes every month whose folder `data/months/YYYY-MM/` is missing or incomplete, then processes the complete raw days after the last month (see "Raw days"), then combines everything, and last writes today so far (see "Today so far"). A second run downloads no month again (AC-1) and no raw day that is done. It reads `data/coords.parquet`, and when the file is missing it fetches the coordinates first (one Wikidata query, before anything else).
- `uv run python -m pipeline.live` makes one run of the live collector for the large stations (see "Live collector"); it needs the DB API key in the environment.

After a change to the per-month logic (cleaning, line names, the bus rule, coverage rule) the existing month folders are stale: delete `data/months/` and run `pipeline.update` again. A change to what a raw day parses (the line number, the trip table) needs `data/days/` deleted too, which downloads the raw days again. A month or raw day folder without the trip table is processed again by itself. The skip check only looks for the folder, not for the version of the code that wrote it.

**Source schema.** The source must carry exactly the 23 known columns (`COLUMNS` in `pipeline/aggregate.py`). A missing or a new column aborts the run with a message that names it (AC-2).

**Month folder** `data/months/YYYY-MM/`, written to a temporary sibling and renamed only when all fifteen files exist, so a crash never leaves a half-complete month (a folder from before the day tables, the hour table, the line section tables, the trip table or the record tables lacks some of them and is processed again by the next run):

**Raw days.** The source's `raw_data` folder (`raw_data/year=/month=/day=/…parquet`, one folder per UTC day, no zero padding) holds the raw DB Timetables API responses: `plan` and `fchg` as IRIS XML in `response_data`, with `url`, `api_name`, `status_code` and `timestamp` (naive UTC). The collector is scheduled four times a day in blocks of six hours (the real runs are irregular, 3 to 6 a day), and a pass over all stations takes about five minutes. A month is about 4.8 GB, about 160 MB a day. Licence as the monthly files (CC BY 4.0, Deutsche Bahn).

- **Which days.** From the first day after the last complete monthly folder, day by day, up to the last complete day. A day D is complete once a complete `fchg` run that started after the local (Europe/Berlin) midnight ending D exists in the folders of D and D+1 (`day_complete`, §3): its late changes are in by then, so yesterday is usually there by about 02:00 to 03:00 local if piebro has uploaded that run. A raw file is one run; a file without any `fchg` (a run whose requests all failed) is no run. Day D reads the folders of UTC D-1, D and D+1: the runs fetch the plan for the local hours 00:00 to 03:00 a day ahead, so it often sits in the folder before D, and the late changes land in the folder after.
- **Folder** `data/days/YYYY-MM-DD/`, written to a temporary sibling and renamed like a month folder:

  | File | Keys |
  |---|---|
  | `days.parquet` | `day`, `gruppe`, `eva`, `bucket`, `n`: the same histogram as a month's, for the stops planned on that day |
  | `hours.parquet` | `hour`, `rows`: the cleaned rows per local hour of `time` on that day, what the gap rule needs |
  | `day_hours.parquet` | the month folder's hour table, for the stops planned on that day |
  | `day_gaps.parquet` | `day`, `missing_hours`: one row, rewritten for every raw day on each update |
  | `runs.parquet` | the month folder's trip table, for the trips that started on that day (the first raw day also takes the earlier trips' stops recorded from its boundary on, by the rule of `days.parquet`) |

- **Superseded by the monthly file.** Once a month's folder under `data/months/` is complete, the raw day folders of that month are deleted and `combine` ignores them: the monthly file wins. The folder of the new first raw day is deleted and processed again too, because the boundary moved (see §3).
- **Downloads are temporary.** Each raw folder is fetched once per run into a temporary directory, kept while the next days need it (three days in a row) and deleted when no later day does; nothing of the raw files stays on disk, about 1 GB at a time.
- **After a network error, run the command again.** There is no retry; a day that is done is skipped without any network call, so the rerun picks up where the failure was.

**Combined files** in `data/`, the only ones the API reads:

One row per (`weekday`, `hour`, `gruppe`, `eva`, `month`, `bucket`) with count `n`. `weekday` 0 = Monday, `hour` from the planned arrival, `gruppe` is `fern` or `regional`, `bucket` is the delay in whole minutes, NULL = cancelled stop. |

| `linienweg.parquet` | `linie`, `pos`, `eva`: the station order (axis) of each line, from the newest month in which the line has routes, by `core.sections.line_axis` ([lines.md](lines.md) §3). |
| `fahrten.parquet` | `linie`, `day`, `trip`, `zug` (the line name where the stop has no train type or number), `num`, `eva`, `an_plan` and `ab_plan` (minutes since the trip day's local midnight, past 1440 for a night trip), `an_delay` and `ab_delay` (change minus planned in minutes, null without a change time, which counts as on time), all four Int16, and the two cancel flags: the stops of the trips of the last 28 days (`WINDOW_DAYS`, ending on the last day of `tage.parquet`), for the lines of `linien.parquet`, sorted by line, day, trip and stop number, in row groups of `FAHRTEN_ROW_GROUP` = 10,000 rows (about the stops of one busy line on one day), so the API reads one line and one day from one or two of them. `combine` reads only the month and raw day folders that reach into the window, and of a stop in two places the first copy stays. A trip finds its line by the line name and the EVA of its first stop, like a section. 56 MB for 13.3 million stops with the months to 2026-10 and the raw days to 2026-11-04; `combine` prints its rows and size. The minutes instead of timestamps keep it small: with the four timestamps the same file was 194 MB. The Bildfahrplan ([lines.md](lines.md)). |
| `monate.parquet` | `month`, `missing_hours`, `stations`: one row per month. The API requires it. |
| `days.parquet` | `day`, `gruppe`, `eva`, `bucket`, `n`: the month files and the raw days summed per key (an edge day can sit in two of them, or in the last month and the first raw day), sorted by day, EVA, group and bucket, in row groups of `DAYS_ROW_GROUP` = 50,000 rows (about one day), so the API's day filters (Live-Lage's one day, the Karte's range) skip the others ([day-history.md](day-history.md) §3). |
| `tage.parquet` | `day`, `missing_hours`: every calendar day from the first month to the last complete raw day, sorted. |
| `day_hours.parquet` | `day`, `hour`, `gruppe`, `eva`, `bucket`, `n`: the hour table of the month files and the raw days, summed per key like `days.parquet`, sorted by day, hour, EVA, group and bucket, in row groups of `DAYS_ROW_GROUP` rows. It holds the large stations only (those of `large.parquet`), so summed over the hour it equals `days.parquet` for those stations. The API reads it for today and for the collector's days, and the Azure deployment downloads it. |
| `large.parquet` | `eva`: the large stations, sorted, written by `combine` right after `monate.parquet` by the one core rule, `core.periods.large_stations` on `days.parquet` and the full-coverage start from `monate.parquet`; empty when no month lies before full coverage. The collector and the API read it, so neither needs the big `days.parquet` for the set. |
| `halte.parquet` | `eva`, `gruppe`, `month`, `n`: the month tables `stops` summed per key, sorted by EVA, month and group. 71,633 rows, 0.2 MB with the months to 2026-10. The station records. |
| `takt.parquet` | `linie`, `gruppe`, `month`, `trips`: the month tables `line_trips` mapped to the line and summed, for the lines of `linien.parquet` only, sorted by line and month. 69,677 rows, 0.2 MB. The trains-per-hour records. |
| `linien_stunden.parquet` | `linie`, `gruppe`, `weekday`, `hour`, `month`, `bucket`, `n`: the month tables `line_hours` mapped to the line, for the lines of `linien.parquet` only, sorted by line and month. 25.2 million rows, 28.9 MB with the months to 2026-10. The heatmap of one line. |

`aggregate.parquet`, `lines.parquet`, `linien.parquet`, `abschnitte.parquet`, `linienweg.parquet`, `halte.parquet`, `takt.parquet`, `linien_stunden.parquet`, `stations.parquet` and `monate.parquet` are built from the month folders only.

**Today so far.** After `combine`, `pipeline.update` writes `data/heute_rest.parquet`, the current local day as far as the raw responses reach:

- It reads the UTC folders of the day before and of today, the way a raw day does, and takes the newest file with a `fchg` pass. If that pass ended on an earlier local day, or there is none, the file gets zero rows and nothing is downloaded.
- `stand` is the start of that pass (UTC), and the cut is the local hour of `stand`: only arrivals planned on today before that hour count, because the stops of the current hour are not settled.
- Only the large stations that answered that pass with a body count (the same set as in `day_hours.parquet`); a station whose request failed would otherwise keep older changes and look on time.
- The content is `day_hours` of those stops plus the constant `stand`, written to a `.tmp` sibling and renamed. It is rewritten on every update and never becomes a folder in `data/days/`, so `combine` and the completeness rule do not see it. Because it runs last, a failing download of today's files never keeps the complete days from being combined.
- It downloads both UTC folders again on every update (about 2 × 160 MB, deleted afterwards).

**Live collector.** `pipeline.live` fetches today's state of the large stations from the DB Timetables API ([adr/0002-live-source.md](adr/0002-live-source.md)):

- **Running it.** Register an application in the DB API Marketplace (plan "Free") and put its two values into the environment, `DB_CLIENT_ID=<client id>` and `DB_API_KEY=<api key>`, kept in an environment file outside the repository; the key is never committed, and the gate's secret scan covers the repository. Then `uv run python -m pipeline.live`. One call is one run and prints one line: the day and the cut, the requests and how many failed, how many stations are ready, and whether the deadline or HTTP 429 stopped it. The line never contains the key. For a fresh today, call it every 15 minutes, by cron or by a loop in the shell; on Azure a scheduled Container Apps job does that with the API's image ([deployment.md](deployment.md) §4). It needs `data/large.parquet` from `pipeline.update`; it does not need the `pipeline` dependency group, because `pipeline.raw` imports the download library only inside `remote_source`.
- **On Azure** (`DATA_URL` set, `sync`): the job's `data/` starts empty, so a run first pulls `large.parquet`, `live_tage.parquet` and the state folders of yesterday and today from that blob container by their public URLs (a 404 means none; any other failure ends the job before the run, because a run without its state would write `live_tage.parquet` from nothing). After the run it uploads every file the run wrote, `live_tage.parquet` and `heute.parquet` before the state folders (so a finished day is in the container before its `final` marker), and deletes the container's blobs under `live/` that the run let go. Writes use a token of the job's user-assigned managed identity (`IDENTITY_ENDPOINT`, `IDENTITY_HEADER`, client id in `AZURE_CLIENT_ID`) with the Blob REST calls `PUT`, `DELETE` and the listing, standard library only. The summary line adds the files uploaded and deleted. `DATA_URL` is the same variable the API reads its files from.
- **Stations.** The EVAs of `data/large.parquet`, which `combine` writes by `core.periods.large_stations`: the stops in the last month before full coverage (`core.periods.full_coverage_start`), 131 stations, the ones the source had before it took every station in. The API uses the same set for Live-Lage.
- **A run.** First `fchg` for every station, then the missing `plan` slices of today before the current hour, station by station, then the slices of the current hour and the next three for all stations. Every slice is fetched once a day. HTTP 429 ends the run's requests. A `plan` slice answered with HTTP 404 is an hour without trains: it counts as fetched and has no stops. Other errors, empty bodies and unparsable XML skip that request, and a skipped slice is asked for again next run. The state and the output are written in any case, except after HTTP 401 or 403: a refused key ends the run at its first such answer with the line `stopped by HTTP <status>: the DB API refused the key` and exit code 1, before anything is written (and on Azure before anything is uploaded), so no further request goes out on a key DB has refused.
- **Rate.** One request per second at most, so never more than the documented 60 a minute; on average about 11 a minute (131 changes per run plus one `plan` slice per local hour, station and day). No request starts later than 12 minutes after the run's start, so runs every 15 minutes do not overlap unless one request hangs for its 30-second timeout.
- **State** in `data/live/YYYY-MM-DD/`: `plan.parquet`, `fchg.parquet` and `slices.parquet`, plus `runs.parquet` (`t0`, the start of each run that got at least one answer, naive UTC) and, once the day is finished, an empty marker file `final`; the XML is parsed with the raw days' rules (`pipeline.raw.parse` and `merge`) and dropped. Folders older than yesterday are deleted.
- **Output** `data/heute.parquet`: `day_hours` of today's arrivals before the last full hour of the run's start, at the stations whose changes came in this run and whose slices before that hour are all in, plus the run's start as `stand` (UTC). It is written to a `.tmp` sibling and renamed. Before 01:00, or when every request failed, it has zero rows.
- **Collector days.** From local midnight on, every run also folds the `fchg` bodies it already fetched into yesterday's state (no extra request) and records its start in yesterday's `runs.parquet`, until yesterday has the `final` marker. The first run that starts at or after 01:00 local, has changes from at least one station and was not cut short (HTTP 429 or the deadline) finalizes yesterday: it writes `day_hours` of the stops planned on that day into `data/live_tage.parquet`, for the stations that have every plan slice of the day (`_hours`: the 24 local hours, 23 on the day the clocks go forward) and answered with changes in that run, replaces the day's rows, keeps the days from `KEEP_DAYS` = 84 days (the 12 reference weeks) before it on, and writes `final`. A day is not kept when the gap between its local midnight, its runs and the finalizing run exceeds `MAX_RUN_GAP` (12 hours), because `fchg` reaches only 13 to 14 hours back; the marker is written anyway, so the day is not tried again. A run that does not qualify for finalizing leaves the day open for the next one. The rows have the shape of `day_hours.parquet`; the API serves the days after the last complete one from this file ([day-history.md](day-history.md) §2).

## 3 Decisions

- **Delay is computed from arrival times** (`arrival_change_time − arrival_planned_time`; no change time = 0 min). Reason: `delay_in_min` in the source is the *departure* delay (arrival delay only at terminal stops), so it is not used.
- **Stops without `arrival_planned_time` are dropped from the delay data** (first stops, about 1.1 million rows per month). Reason: they have no arrival to measure. They still feed the line networks, because a first stop belongs to its trip.
- **Buses and rail replacement are excluded** (`Bus`, `bus`, `Bsv`, `BSv`, `SEV`); a stop without a train type is kept (`is_excluded_expr` is false for a null type). Reason: the product covers rail only, the dataset contains them.
  - **Replacement buses booked under a rail type are dropped by their line name** (`bus_line_expr`: `SEV` or `Bus` as a whole word, digits allowed right after it, case-insensitive; a missing name stays). It runs in `_rail` with the type rule, so every table of a month and of a raw day drops them. Measured on 2024-07 to 2026-10: 3,554 rows, no rail name among them; word-glued names such as `REBUS6` stay on purpose. Reason: "SEV BUS Engen - Singen" (type SBB) passed the type filter and topped the best lines.
- **Month is taken from `time`**, not from the planned arrival. Reason: a monthly file contains stops planned on the last day of the previous or the first day of the next month; `time` lies exactly within the file month.
- **Stations are identified by EVA; names are not unique.** Reason: the dataset has about 5,200 EVAs and some names occur twice (e.g. Hamburg Hbf with two EVAs). The UI shows "name (EVA)"; filters use the EVA only.
- **Cancelled stops are a NULL bucket**, never 0 min. Reason: a cancelled train is not an on-time train (AC-7); the cancellation rate is computed from the NULL bucket.
- **Delay histogram instead of precomputed median/P90.** Reason: percentiles cannot be merged across cells, and filters (period, station) must re-aggregate.
- **Category group by a fixed list**: `ICE, IC, EC, ECE, TGV, RJ, RJX, NJ, EN` are long-distance (`fern`), everything else is `regional`. Reason: the filter is required, the mapping is not specified.
- **Cleaning, per month, in this order:**
  - Delays below −30 min or above +1440 min (24 h, both bounds inclusive) are dropped as implausible. Cancelled stops are kept whatever their times say. A missing change time is plausible. Reason: the observed range is −150 to +1428 min; a delay beyond a day or an arrival half an hour early is a data error, not train behaviour.
  - Duplicates on (`eva`, `train_type`, `train_number`, `arrival_planned_time`) are dropped, keeping the first. Rows without an arrival are never duplicates. Reason: the source repeats stops, and a repeated stop would count twice. This runs after the plausibility rule, so a plausible copy survives an implausible first one.
  - The run prints how many rows each rule dropped per month (3–1,118 duplicates and 158–1,241 implausible rows per month, measured on 2024-07 to 2026-09).
- **No clamp.** The bucket is the exact minute. Reason: clamping hid the long tail from P90 and from the share of delays over an hour; the histogram stays small anyway.
- **A line is its name split into networks.** The name is `line_number`, or `"{train_type} {train_number}"` where that is missing (long-distance trains and a few regional ones, e.g. "ICE 679"). Reason: "S1" alone exists in 15 federal states and splits into 14 networks. Details:
  - **The train type goes in front of a bare number, for every train type** ("57" with RE becomes "RE57", "35" with FLX becomes "FLX35"), and letters and digits lose a space between them ("RE 3" becomes "RE3"). Reason: until the December 2025 timetable change the source gives regional lines as bare numbers and from then on prefixed. Without the rule one line splits in two (`57` and `RE57`), and S1, RE1 and IRE1 sharing a station merge into one line with mixed statistics.
  - Within one name, stations that share a `train_line_ride_id` belong to one network, transitively. A ride id is a trip pattern that repeats daily; 817 ride ids carry more than one name, so (name, ride id) is the unit, not the ride id alone. The networks are connected components, found by min-label propagation in `core/lines.py`.
  - Each month gets its own networks; the combine step joins them across months, with (month, network) standing in for a trip.
  - **Id** `"{name}:{lowest EVA of the network}"`, with the name as built above. It stays the same as months are added, unless a network gains a station with a lower EVA or merges with another one; a saved link to a line can then point at nothing.
  - **Label** names the line's two most frequent end stations by stops, e.g. "RE57 Dortmund Hbf – Warburg (Westf)"; ties go to the lower name. A train-number line ("ICE 679", one direction) reads "ICE 679 → Kassel-Wilhelmshöhe". With one end station the label is the name and that end, with none the name alone. Reason: the name alone does not say where a line runs, and the same name in two networks (S1) must be told apart. **Typ** is the most frequent `train_type` of the line and serves as the badge.
  - **End stations** come from `final_destination_station`; `destination_expr` fixes the spelling ("Schwerte(Ruhr)" becomes "Schwerte (Ruhr)", "Langenhagen - Kaltenweide" becomes "Langenhagen-Kaltenweide"). Null or blank destinations are left out. Reason: the column has 4,647 spellings, and the fix leaves only 32 duplicate groups.
  - A network that only has stops without an arrival (no delay data) is not a line: `linien.parquet` lists only networks with stops, so no row has an empty label or typ. Most lines are single long-distance train numbers. Rankings filter by minimum sample.
- **Missing hours are recorded per month, not repaired.** The usual level of an hour of the day is the lowest, over the seven weekdays, of the median row count of that (weekday, hour) in the month. An hour counts as a gap when it has fewer than `GAP_SHARE` (half) of that level in `pipeline/aggregate.py`; an hour with no rows at all counts too. Reason: the source is quiet at night and on Sunday mornings, so a fixed threshold, or the median over all days, would flag normal hours, while a relative rule also catches a half-empty hour. The hours are counted against the real local month, so the skipped hour of the March clock change is not a gap and the doubled October hour is not one either. The months after the station jump (2025-11) stay flagged for the days before 2025-11-02. Measured on 2024-07 to 2026-09, this flags 50 h in 2025-11, 4–12 h in 2024-11 and in six months between 2026-02 and 2026-08 (2026-07: 8 h), 1 h in 2025-06 and 2025-07, and none elsewhere. SPEC §4.1 names 102 h for July 2026; the way it counts is not known, so the figures can differ.
- **Missing hours are also counted per day** (`day_gaps`), with the same rule and the same hour table (`hour_table` in `pipeline/aggregate.py`) as the month figure, so the days of a month add up to its `missing_hours`. Reason: the daily series and the day map must know which days are incomplete. The day is the calendar day of the poll time, while the delay histogram's day is the planned arrival (see [day-history.md](day-history.md) §3).
- **`hour_table` is the one gap rule.** It takes the row count per hour over a range, adds the hours with no rows as 0, computes the usual level and marks the thin hours. The monthly figures (`_hour_counts`, for `meta` and `day_gaps`) call it with the month, the raw days (`raw_gaps`) with the days of the month so far. Reason: one definition of a missing hour, however much of the month is there.
- **The current month's days come from the raw responses, for the day views only.** Reason: the monthly file arrives after the month ends, so the day map and the daily series stopped up to five weeks back. Heatmap, rankings and the month views keep whole months, because a partial month would skew them (the product owner chose this). The raw days stand in until the monthly file replaces them.
- **Our own minimal parser** (`pipeline/raw.py`, stdlib `xml.etree`), not piebro's code. Reason: it needs only the columns that `clean`, `days` and `day_gaps` read, and piebro's release code is a reference, nothing is copied. The other columns are filled with NULL, so the schema check and the existing table functions apply unchanged. Source and responses are DB's own data via a public dataset; `xml.etree` is not hardened against hostile XML, and expat limits entity expansion.
- **How `plan` and `fchg` combine**, as piebro's monthly release does:
  - Files are read in time order, the responses of a file by `timestamp`; only HTTP 200 and non-empty responses count.
  - From `plan`, the latest snapshot per stop `id` gives type, number and the planned times.
  - From `fchg`, a snapshot replaces an earlier one of the same `id`, as a whole, only if it carries change data: `ct`, `clt`, `cs` or `ps="a"` on `ar` or `dp`, a `tl` of type `e`, or a `ref/tl` with attributes. Messages alone never replace one.
  - Full outer join on `id`. The planned time is the plan's, else the change's. The arrival change time is the `ct`, else the planned time; `time` is the departure change time, else the arrival change time. A stop is cancelled by `cs="c"` or a `clt`; it stays a NULL bucket in `days`, never 0 minutes.
  - The EVA comes from the request URL (zero-padded like the monthly files). `timestamp` is naive UTC, the stop times are local.
- **A raw day holds the stops planned on it, but only those recorded at or after the first raw day's 00:00.** Reason: the day key of `days` is the planned arrival, and the month comes from `time` (the "Month is taken from `time`" decision); a stop planned on the first raw day but recorded before midnight is already in the last monthly file, so summing raw and monthly never counts a stop twice.
  - The first raw day also keeps the stops planned on an earlier day but recorded at or after the boundary: the late stops of the last monthly day (about 0.2 % of it, mostly delayed ones), counted under their planned day. Without them that day would look slightly too punctual for a month.
  - When a monthly file arrives, the boundary moves a month on and the new first raw day is processed again under it; its folder is deleted first, so a crash leaves it to be redone.
- **A raw day reads three UTC folders: D-1, D and D+1.** Reason: the runs fetch the plan for the local hours 00:00 to 03:00 a day ahead, so it often sits in the folder before D, and that run's `fchg` pass is the last one that holds those stops. With only D and D+1, 17 of the 29 days of the first real run had under 2,000 rows in hour 0 (about 9,700 is normal) and six October days were flagged as gaps that were artefacts. A folder is used by three days in a row, so each is downloaded once per run.
- **A raw day D is complete at the first complete `fchg` run that started after the local midnight ending D** (`day_complete` in `pipeline/update.py`, with `core.periods.local_midnight_utc`, which follows the daylight-saving changes). Reason: measured on 7 October days, for the 131 large stations and for all stations, a day folded with the first complete run after local midnight equals the day settled by the morning run: Germany within 0.01 %-points in punctuality and cancellations (0.005 over all stations), 0 minutes in median and P90, the same Germany class in every metric, at most one station class changed of the 131, no station missing. A run before midnight gives a day 1.2 to 2.0 %-points too good, because the stops after it have no change yet. The old rule, a snapshot after D+1 06:00 UTC, only waited for the morning run and made every page lag by about 8 hours.
  - **What counts as a run.** `RawSource.fchg_span(key)` returns the time of a file's first and last `fchg` request and their number. Files whose first request lies within `SAME_RUN` = 60 s of the previous file's last are one run (a run can be split over two files at UTC midnight; seen on 2026-10-22/23, with 32 of the 131 large stations in the first half). The last run counts only if it does not end within 60 s before a UTC midnight, since its other half may still be missing; a later file settles that. A run with fewer requests than `FULL_RUN` = 90 % of the largest run among the files died partway: the stations it never asked would count their late stops as on time, so it does not complete the day.
  - **Which files.** The first run after local midnight (22:00 or 23:00 UTC) still sits in the folder of D, so the check reads the files of the UTC folders of D and D+1: about 12 small remote reads (two columns and a count) per pending day.
- **Raw days are re-judged for gaps on every update.** The usual level of an hour grows with the month, so every raw day is judged again against the raw days of its month so far, from the stored `hours.parquet` and without downloading anything. Hours after the last complete day are never missing.
- **Duplicates keep the first in `time`, then `id` order.** Reason: the monthly release sorts by `time` and leaves ties open, so no rule on the id can reproduce it; the id order at least makes the raw result reproducible.
- **Equivalence with the monthly file was checked on four past days** (see the milestone). Reason: the product owner wanted exact or a stated cause before any tolerance.
- **Timetable changes are marked, not split.** `core.periods.timetable_changes` returns the Sunday after the second Saturday of December (2024-12-15, 2025-12-14, 2026-12-13). The API lists those inside the data range and trains keep one key across years. Reason: product owner's choice (SPEC O6); splitting statistics per timetable period comes with the planner, where train numbers matter.
- **Full coverage starts where the station count jumps.** `core.periods.full_coverage_start` returns the first month with at least half as many stations as the largest month. The source has about 135 stations per month until 2025-10 and about 5,2xx from 2025-11, so it returns 2025-11. Reason: views default to the period where "nationwide" is true.
- **`large.parquet` holds the large stations as a file.** Reason: the collector and the API need the set, and reading it from the 38 MB `days.parquet` would make that file a requirement wherever the collector runs. The rule stays in one place, `core.periods.large_stations`; `combine` evaluates it and everything else reads the result.
- **The hour table is `days` with the planned arrival hour in the keys** (`day_hours`, both through `_per_day`), over all days. Reason: the reference days of today are cut at the hour today has reached, with all four metrics ([adr/0002-live-source.md](adr/0002-live-source.md)). `days.parquet` stays as it is, so the existing day views are unchanged.
- **The live collector and the partial day reuse the raw days' parser.** `stop_rows` is `parse` (fold one response into the `plan` and `fchg` dicts) plus `merge` (dicts to stop rows); the collector calls both steps, so live, raw and partial days follow one set of rules. The decisions about today (the cut, the deadline, which stations count, `stand`) are in [day-history.md](day-history.md) §3.
- **Local time comes from `core.periods.local_time`** (Polars' time zone rules), not from `zoneinfo`. Reason: Windows has no `tzdata`, and no package is added for it.
- **The line number of a raw day comes from the XML.** `parse` keeps the `l` attribute of the arrival, else of the departure (`p_l` in the plan, `f_l` in the changes, appended last so a collector state file from before still loads, `pipeline.live._stops` pads the missing column), and `merge` writes `line_number` as the plan's value, else the change's; a blank `l` is none. Reason: the trip table's line name needs it, and a raw day without it named every trip by type and number. A blank `line_number` counts as missing everywhere (`line_name_expr`), so the line reads "ICE 679" and no nameless line forms. Not yet confirmed on real data: whether `l` of long-distance trains equals the monthly file's value (the platform check in [lines.md](lines.md) §6).
- **Line sections and routes come from the trip key in `id` and are the one place that uses first stops' departure delay.** A trip is `id` without its last part, the stop order its stop number (`train_line_station_num`, else that last part), and a section joins two consecutive numbers; the `minutes` of a section are the sum of the delay changes. The rules, their reasons and the real-data check are in [lines.md](lines.md) §3, so this file does not repeat them. Both tables are built from the cleaned rows (stops without an arrival included, since a first stop hands its departure delay to the first section), per month of the end stop's `time`, and a source without ids gives empty tables with the right schema. `combine` maps a section to its line by line name and first station (`line_ids`), as `lines.parquet` does, and takes the axis from the newest month in which the line has routes (§8). Measured on 2026-10: `sections` 47,130 rows and `routes` 23,654 rows a month, about 0.6 MB together, 8 to 9 s each on top of the month run.
- **The record tables are three small month tables, joined to the line in `combine`.** `stops` counts every stop (the aggregate counts arrivals only, so a terminus's starting trains would be missing), `line_trips` the trips that start between 06:00 and 21:59 local, `line_hours` is `lines` with weekday and hour instead of the station. Reason: trains per hour has no source per period (`fahrten.parquet` covers 28 days, the month `runs.parquet` costs gigabytes to read), and a line heatmap needs the line in the key where the aggregate has the station. A month folder without them is processed again, which is the one rebuild. A line's `net` is the month network's lowest EVA, so `write_line_profiles` maps (`name`, `net`) to the line by `line_of` like the other line tables. Measured on `halte` and `takt` with the months to 2026-10: 0.2 MB each; `linien_stunden` is 28.9 MB, below the 40 to 60 MB that was estimated from one month.
- **Output size** (measured on 2024-07 to 2026-09 unless a date says otherwise): `aggregate.parquet` 60.8 MB, `lines.parquet` 10.9 MB, `linien.parquet` 0.2 MB, `stations.parquet` 0.1 MB, `monate.parquet` under 0.1 MB. With the months to 2026-10, `abschnitte.parquet` is 2.9 MB and `linienweg.parquet` 0.24 MB. The per-day histogram adds about 36 MB (estimated on 2025-06 and 2026-09); the real file was 36.7 MB, 0.3 % more with the row groups, and 39.5 MB once the October 2026 raw days were in ([day-history.md](day-history.md) §5). The hour table `day_hours.parquet` holds the 131 large stations only and is 24.9 MB with the raw days up to 2026-10-30 (19.3 million rows; for all stations it was 231 MB and 106.0 million rows). The 2 GB limit of AC-3 is far away, so no watchlist fallback is needed.

## 4 Architecture and data keys

- `pipeline/aggregate.py`: per-month tables from one source file, read lazily with Polars. `check_schema` validates, `clean` applies the cleaning, and `aggregate`, `lines`, `ends`, `month_networks`, `stations`, `meta`, `days`, `day_gaps`, `day_hours`, `sections`, `routes`, `runs`, `line_hours`, `line_trips` and `stop_counts` (file `stops`) build the fifteen month tables (`days` and `day_hours` share `_per_day`, `sections`, `routes`, `runs` and `line_trips` share `_trip_stops`, `line_hours` and `lines` share the arrival rows). `with_coords` and `coverage_report` serve the combine step.
- `pipeline/update.py`: `update` walks the remote months and calls `process` for each incomplete one, then `update_days` for the raw days, then `combine`, then (when `main` passes a clock) `update_rest` for today so far. The downloader, the list of remote months and the raw source (`RawSource`: list a UTC day's files, read a file's `fchg_span`, download a file) are passed in, so tests run it with fakes that count their calls. `combine` writes the combined files, `write_large`, `write_line_sections` (`abschnitte.parquet`, `linienweg.parquet`), `write_line_profiles` (`linien_stunden.parquet`, `takt.parquet`; `halte.parquet` is written inline) and `write_trips` (`fahrten.parquet`, called last) among them; `MONTH_FILES` lists the month tables, so a month folder without one of them counts as incomplete. `update_days` deletes leftover `.tmp` folders and the day folders of complete months (the new first day first), then walks from the first day after the last month to the first incomplete day; `process_day` writes one folder, `_write_gaps` re-judges all of them, `_raw_dirs` lists the folders `combine` adds (`DAY_FILES`: `days`, `hours`, `day_hours`, `runs`). `day_complete(raw, keys, day)` decides whether a raw day is complete (§3; constants `SAME_RUN`, `FULL_RUN`), with `core.periods.local_midnight_utc` for the local midnight in UTC. `write_large(data_dir)` writes `large.parquet`. `newest_fchg` finds the newest file with a `fchg` snapshot, looking back past files without one, for `update_rest`, which writes `heute_rest.parquet`.
- `pipeline/raw.py`: `stop_rows` parses `plan` and `fchg` into one row per stop id in the monthly schema, as `parse` (one response into the dicts) and `merge` (the dicts into rows); `fchg_pass` gives a file's `fchg` pass start and the stations that answered with a body; `RawSource.fchg_span` gives the first and last `fchg` request time of a file and their number; `day_tables` returns `days`, `hours` and `day_hours` of one day and `day_runs` the trip table of one day; `raw_gaps` returns the missing hours per raw day through `hour_table`; `remote_source` is the real `RawSource` (the HuggingFace listing per day folder, a remote read of the two columns `api_name` and `timestamp`, the download; it is the only place that imports `huggingface_hub`, so the collector runs without it).
- `pipeline/live.py`: the live collector (`run`, `large_evas`, `_finalize`, `sync`, `main`; see §2, "Live collector"). Its `large_evas` reads `data/large.parquet`, the set `combine` and `update_rest` keep in `day_hours.parquet` and `heute_rest.parquet`; `run` exits naming `pipeline.update` when it is empty. Its constants are listed in [day-history.md](day-history.md) §4.
- `core/lines.py`, `core/periods.py`, `core/delay.py`, `core/holidays.py`, `core/sections.py`: the pure parts (line names, end-station spelling and networks, timetable changes, coverage start, the large stations and German local time, the delay and plausibility rules, the nationwide public holidays: fixed dates plus the Easter-based ones, no library; regional holidays are not included; the trip key and stop number from `id`, the section changes and the line axis, [lines.md](lines.md)).
- `data/coords.parquet`: `ibnr`, `lat`, `lon`, `land`, one row per IBNR for the whole of Wikidata (not only Germany). The join strips the leading zero of our EVA (`08000207` to `8000207`) with `core.stations.ibnr_expr`. An EVA without a match takes the coordinates of the one located station with exactly the same name (secondary EVAs such as S-Bahn platforms). Details and the source decision: [adr/0001-station-coordinates.md](adr/0001-station-coordinates.md).
- `data/stations.parquet`: `n` is all stops of the EVA in the source, arrival stops with cancelled ones included; it ranks search results and sizes map dots. `lat`, `lon` and `land` are NULL where Wikidata has no match or no state.
- Coverage report, printed by the combine step: named stations with coordinates (number and share), the share of stops that belong to them, and the unmatched named stations with the most stops. Measured on the months to 2026-09: 5,418 of 5,419 named stations (100.0 %, as the report rounds it). Unmatched: Trebitz (b Könnern), one stop, no Wikidata item.
- The source also contains `xml_station_name`, `id`, `is_additional_stop`, the departure columns and more; most are not used yet.
- Time zone: Europe/Berlin, as in the source; the stop times are not converted. The request times (`timestamp` of the raw files, the collector's clock) are UTC; where they decide a local day or hour (today, the cut), `core.periods.local_time` converts them.

## 8 Known shortcuts

- The skip check looks only at the month folder (`ponytail:` comment in `_complete`): a month file that HuggingFace replaces later is not fetched again, and month folders carry no version. Changing the per-month logic needs `data/months/` deleted by hand (see §2).
- Downloads use no pinned dataset `revision` (`ponytail:` comment in `download` and `remote_source`). If the upstream dataset re-uploads a month, a newly fetched month and the older processed ones can come from different upstream states without notice. Revisit when upstream corrections matter: record the dataset commit in `meta` and reprocess the months whose commit differs.
- The combine step rewrites every combined file on every run, also when no month is new (`ponytail:` comment in `combine`).
- The line axis comes from the newest month in which the line has routes (`ponytail:` comment in `write_line_sections`); the reason and the ceiling are in [lines.md](lines.md) §8.
- **The record tables hold whole months only**, like the section tables: the current month's raw days are in none of `halte`, `takt` and `linien_stunden`. `linien_stunden.parquet` (28.9 MB) is downloaded whole at every cold start on Azure, though one request reads one line.
- The monthly source files stay in `data/raw/` after processing, about 5 GB for the months to 2026-09. The raw-day downloads are deleted after processing.
- **Tie-break noise in raw days.** About 3 stops a day (one train's two ids with the same `time`) keep the other duplicate than the monthly file does and sit 1 to 2 minutes off. It ends when the monthly file replaces the raw days (`ponytail:` comment in `day_tables`).
- **An early-month gap may stay unflagged.** The raw days' usual level comes from the raw days of the month so far, one value per weekday early on, so a gap is found only once its weekday has come round about three times. A gap in the first two weeks of a month may stay unflagged until the monthly file arrives. Pooling the previous month's level would fix it (`ponytail:` comment in `raw_gaps`).
- **No retry on network errors** in `remote_source` (`ponytail:` comment there): a failure stops the run, and running it again is the remedy; days that are done are skipped.
- **Raw downloads are not kept.** A day's raw files are downloaded again if its folder is lost or the parse logic changes (`ponytail:` comment in `update_days`); keeping them would cost about 250 MB a day. After a change to the parsing, delete `data/days/` and run `pipeline.update` again.
- **An empty folder after a day stalls the later days.** If the source loses a whole UTC day, the folder of D+1 is empty, the completeness check never passes and no day after D is processed until the folder appears or the monthly file arrives (`ponytail:` comment in `update_days`). A day whose own folder is empty is processed from its neighbours and prints a warning; the gap rule flags it. Skipping over an empty folder needs a rule for the day after.
- `combine` fails when no month folder is complete; it only happens if the remote list is empty.
- **Splits are assumed only at UTC midnight.** `day_complete` holds back a last run that ends within 60 s before a UTC midnight, since its other half may be missing; one observed split in seven nights was exactly there. A run split elsewhere would complete a day too early. Comparing the stations that answered with the run before would catch it, at the price of downloading files to decide whether to download the day.
- **`day_complete` reads the span of every file of two UTC folders** from the remote, about 12 small reads per pending day and update, where one lookup used to do. Cheap enough at one update a run; keep the spans in a local cache if updates get slow.
- The shortcuts of today (the partial day's repeated download, the collector's catch-up, its frozen station list and whole-state rewrite) are listed in [day-history.md](day-history.md) §8.
- `pipeline.coords` is not run by tests or the gate (it needs the network); only its parser is tested, on canned JSON.
- The end-station spelling fix is a regex (`ponytail:` comment in `destination_expr`). Variants such as "Bahnhof, Arnsberg" stay separate; map destinations to station EVAs if they show in labels.
- The train type comes from `train_type` before December 2025 and from `line_number` after. A line the source typed differently before the change (RB68 then, RE68 now; IRE1 then, ARV1 now) stays a separate line that ends in 2025-11. Measured on the months to 2026-09, that is 77 lines and 0.045 % of stops; revisit if one shows up in the rankings.
- A line is shown as a train-number line (label with "→") when its name matches `^\S+ \d+$` (`ponytail:` comment in `line_table`). A source line number with a space before the digits would match too; 2 such labels exist in the real data.
